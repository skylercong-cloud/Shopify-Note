二、Product 到底是什么？

你可以把 Product 理解成：

消费者眼中的“一个商品”。

例如：

文本
Nike Air Max

它可能有：

文本
Title:
Nike Air Max

Description:
Running shoes...

Vendor:
Nike

Product Type:
Running Shoes

Tags:
running, nike, shoes

Options:
Color
Size

Variants:
6 个

Media:
8 张图片
2 个视频

Collections:
Running Shoes
Nike
Featured

所以 Product 是一个商品容器 / 商品主体。

三、Variant 是什么？

Variant 是：

这个 Product 下真正可以购买的具体规格组合。

例如：

文本
Product:
T-Shirt

Options:
Color
Size

有：

文本
Color:
Black
White

Size:
S
M
L

最终 Variant：

文本
Black / S
Black / M
Black / L

White / S
White / M
White / L

每一个 Variant 都是一个独立的可购买实体。

四、为什么 Shopify 要把 Product 和 Variant 分开？

这是理解 Shopify 数据模型最关键的一步。

假设：

文本
Nike Air Max

有：

文本
Black / 8   $100
Black / 9   $105
Black / 10  $110

如果没有 Variant：

文本
Nike Air Max

只能有：

文本
price = ?
sku = ?
inventory = ?

问题来了：

到底哪个价格？

到底哪个库存？

到底哪个 SKU？

所以：

文本
Product
   │
   ├── Variant A
   │     price
   │     sku
   │     inventory
   │
   ├── Variant B
   │     price
   │     sku
   │     inventory
   │
   └── Variant C
         price
         sku
         inventory

这些具体商业属性应该落到 Variant。

五、Product Option 和 Variant 的关系

这是另一个很容易混的地方。

例如：

文本
Product
│
├── Option 1: Color
│      ├── Black
│      └── White
│
└── Option 2: Size
       ├── S
       ├── M
       └── L

Option 是：

规格维度。

而 Variant 是：

规格维度的具体组合。

所以：

文本
Color = Black
Size = M

组合起来：

文本
Black / M

这才是一个 Variant。

六、从前端角度看 Variant

这就是我们之前写过的：

liquid
{% for variant in product.variants %}

  {{ variant.id }}
  {{ variant.title }}
  {{ variant.price }}
  {{ variant.available }}

{% endfor %}

例如：

文本
Variant
├── id: 123456
├── title: Black / M
├── price: $29.99
├── sku: TS-BLK-M
└── available: true

前端真正 Add to Cart 的时候：

文本
User
 ↓
选择 Black
 ↓
选择 M
 ↓
找到 Black/M Variant
 ↓
Variant ID
 ↓
Cart

所以：

购物车加的不是 Product，而是 Variant。

这是非常重要的一句话。

七、Product ID 和 Variant ID 是两个不同 ID

例如：

文本
Product ID
= 1001

Variant ID
= 2001

关系：

文本
Product 1001
│
├── Variant 2001
├── Variant 2002
└── Variant 2003

所以不要写：

js
addToCart(product.id)

而应该：

js
addToCart(variant.id)

这就是为什么我们之前的 Product Form：

liquid
<select name="id">
  {% for variant in product.variants %}
    <option value="{{ variant.id }}">
      {{ variant.title }}
    </option>
  {% endfor %}
</select>

里面：

html
name="id"

实际上提交的是：

Variant ID

八、Variant 最重要的几个字段

你现在重点记这些：

文本
Variant
│
├── id
├── title
├── sku
├── barcode
├── price
├── compare_at_price
├── available
├── options
├── featured_image / media
└── inventory

其中：

id

Variant 唯一标识。

title

例如：

文本
Black / M

它通常是 Variant 的规格组合展示名称。

sku

库存管理 / ERP / OMS 等系统经常使用：

文本
TS-BLK-M

SKU 和 Shopify Variant ID 不是一个概念。

barcode

例如：

文本
6901234567890

可能用于：

文本
商品条码
仓库扫描
POS
物流

price

Variant 的价格。

compare_at_price

例如：

文本
compare_at_price = $59.99
price = $39.99

Theme 可能展示：

文本
$59.99  ~~$39.99~~

具体展示逻辑由 Theme 决定。

九、available 不等于“库存数量”

这是一个非常重要的区别。

例如：

liquid
{{ variant.available }}

得到：

文本
true

这只能告诉 Theme：

当前 Variant 是否可购买。

它不是：

文本
inventory_quantity = 37

所以不要理解成：

js
variant.available === true

意味着：

文本
库存 = 1+

它是更高层次的可购买状态。

后面我们专门学 Inventory 时再把：

文本
InventoryItem
InventoryLevel
Location
available

全部拆开。

十、Variant 和 Media

Variant 也可以和商品图片/媒体产生关联。

例如：

文本
Product
│
├── Black
│    └── Black Product Image
│
└── White
     └── White Product Image

用户：

文本
选择 Black

Theme：

文本
Variant selected
 ↓
Variant Media
 ↓
Gallery switch

所以我们之前学 Product Media 时：

文本
Product Media
+
Variant

实际上已经开始接触这个数据模型。

十一、Product 和 Collection 的关系

这个也非常重要。

很多初学者容易想成：

文本
Collection
   │
   └── Product

好像 Product 只能属于一个 Collection。

实际上不是。

一个 Product 可以属于多个 Collection：

文本
Nike Air Max
   │
   ├── Running Shoes
   ├── Nike
   ├── Best Sellers
   └── Men's Shoes

所以：

文本
Product
 ↕
Collections

更接近：

多对多关系。

这也是为什么我们之前讲 Collection 时说：

Collection 不是 Product 的父对象。

十二、Product 和 Metafield

再连接我们之前学过的 Metafield：

文本
Product
│
├── title
├── description
├── vendor
├── tags
│
└── metafields
      ├── custom.material
      ├── custom.origin
      ├── custom.size_guide
      └── custom.rating

所以：

文本
Product
+
Metafield

可以扩展 Shopify 原生 Product 数据。

例如：

文本
custom.material = Cotton
custom.origin = China

Theme：

liquid
{{ product.metafields.custom.material.value }}

十三、Product / Variant / Metafield 的层级

现在非常值得记住：

文本

│
├── Product-level data
│   ├── title

│   ├── vendor
│   └── ...
│
├── Product Metafields
│   ├── material
│   ├── origin
│   └── ...
│
└── Variants

    ├── Variant A
    │   ├── price

    │   └── ...
    │
    ├── Variant B
    │   ├── price
    │   ├── sku
    │   └── ...

十五、为什么 Variant 会影响前端这么多功能？

因为 Variant 是整个电商购买链路的核心。

文本
Product
   │
   ▼
用户选择 Option
   │
   ▼
匹配 Variant
   │
   ├── Price
   ├── Compare Price
   ├── SKU
   ├── Availability
   ├── Media
   └── Inventory
   │
   ▼
Variant ID
   │
   ▼
Cart
   │
   ▼
Checkout
   │
   ▼
Order

所以你以后看到：

文本
Product
Variant
Cart
Order
Inventory

千万不要把它们当成孤立的数据。

它们是一条链。

十六、最重要的概念：购买单位

我们可以用一个非常简单的问题判断 Product 和 Variant：

客户最终买的到底是什么？

例如：

文本
客户：
我要买 Nike Air Max

实际上系统需要知道：

文本
Nike Air Max
Color = Black
Size = 9

于是系统找到：

文本
Variant ID = 987654

然后：

文本
Variant 987654
Quantity = 1

进入 Cart。

所以：

Variant 才是购物交易中的具体购买单位。

十七、这和数据库设计很像

如果你有数据库经验，可以粗略理解：

文本
products
────────────
id
title
description
vendor
...

        1
        │
        │
        │ N

product_variants
────────────────
id
product_id
sku
price
barcode
...

关系：

文本
products
   1
   │
   └────── N
          variants

但是 Shopify 内部真实的数据模型远比这个复杂，尤其是 Inventory、Media、Metafield、Selling Plans 等，所以这里先用这个模型建立认知。

十八、为什么 Shopify API 用 GraphQL 后会感觉复杂？

因为你之后会看到类似：

graphql
product(id: "...") {
  id
  title

  variants(first: 10) {
    nodes {
      id
      title
      price
      sku
    }
  }
}

这个时候你就不会觉得奇怪：

文本
Product
   │
   └── variants
           │
           ├── Variant
           ├── Variant
           └── Variant

这就是我们现在建立的数据模型。

十九、GraphQL mental model

以后你学习 Shopify Admin GraphQL API 时：

graphql
product {
  title
  variants {
    nodes {
      id
      sku
      price
    }
  }
}

你应该脑子里马上出现：

文本
Product
│
├── title
│
└── Variants
     ├── id
     ├── sku
     └── price

而不是把 GraphQL 当成一堆陌生语法。
