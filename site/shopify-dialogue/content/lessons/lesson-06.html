第 6 课：Liquid 深入 —— Shopify Theme 的“模板引擎”

这一课非常重要。

如果把你熟悉的 React/Next.js 开发拿来类比：

Liquid ≈ Shopify 世界里的模板渲染语言。

但它和 React 有一个非常大的区别：

React 主要在浏览器/服务端运行 JavaScript；
Liquid 是 Shopify 在服务器端执行，然后生成 HTML。

一、先建立一个最重要的运行模型

你以后看到 Shopify Theme 代码，脑子里应该自动出现：

文本
Shopify 数据
    ↓
Liquid
    ↓
HTML
    ↓
浏览器
    ↓
JavaScript
    ↓
用户交互

例如 Shopify 里面有一个 Product：

文本
Product
title = "Classic T-Shirt"
price = $29.99

Theme 中：

liquid
<h1>{{ product.title }}</h1>

Shopify 服务器执行 Liquid 后：

html
<h1>Classic T-Shirt</h1>

然后浏览器拿到的是：

html
<h1>Classic T-Shirt</h1>

浏览器根本不知道 {{ product.title }} 是什么。

这点一定要记住。

二、Liquid 最核心的 3 种语法

你以后 80% 的 Liquid 代码，基本都可以归到这三类。

① 输出数据：{{ }}

例如：

liquid
{{ product.title }}

输出：

文本
Classic T-Shirt

再比如：

liquid
{{ product.vendor }}
liquid
{{ product.description }}
liquid
{{ product.price }}

② 执行逻辑：{% %}

例如：

liquid
{% if product.available %}
  <button>Add to cart</button>
{% else %}
  <button disabled>Sold out</button>
{% endif %}

这里：

liquid
{% if ... %}

不是输出内容。

它是在告诉 Shopify：

“判断一下这个商品是否可以买。”

③ 注释：{# #}？

这里要特别注意：

Liquid 不是：

liquid
{# comment #}

而是：

liquid
{% comment %}
这是注释
{% endcomment %}

这是 Shopify 开发和普通模板语言非常不一样的地方。

产品变体到底是什么？

我的追问09-19 19:14

麻烦你再给我解释下产品变体的概念

ChatGPT 讲解09-19 19:14

当然可以。Product Variant（产品变体）是 Shopify 里非常核心的概念，而且它和普通前端开发里的“商品属性”有一点区别。

你可以先记住一句话：

Product 是“卖什么”，Variant 是“具体卖哪一个”。

1. 用最直观的例子理解

假设你在 Shopify 卖一件 T 恤：

Product：

Classic T-Shirt

但是这件 T 恤有：

  • 黑色 / S
  • 黑色 / M
  • 黑色 / L
  • 白色 / S
  • 白色 / M
  • 白色 / L

那么：

文本
Product
└── Classic T-Shirt
      │
      ├── Variant 1：Black / S
      ├── Variant 2：Black / M
      ├── Variant 3：Black / L
      ├── Variant 4：White / S
      ├── Variant 5：White / M
      └── Variant 6：White / L

这里：

Classic T-Shirt 是 Product

而：

Black / M 是一个 Variant

2. 为什么 Shopify 要把 Product 和 Variant 分开？

因为消费者看到的是：

我要买一件 T-Shirt。

但是仓库真正需要知道的是：

我要发 黑色、M码 的这一件。

所以：

文本
Product
= 商品概念

而：

文本
Variant
= 可以被单独购买、库存管理的具体规格

例如：

Product Variant SKU 库存
Classic T-Shirt Black / S TS-BLK-S 20
Classic T-Shirt Black / M TS-BLK-M 15
Classic T-Shirt Black / L TS-BLK-L 8
Classic T-Shirt White / S TS-WHT-S 12
Classic T-Shirt White / M TS-WHT-M 25

这里你就能看到一个非常重要的事情：

库存不是简单地属于 Product，而是和具体 Variant 相关。

3. Variant 和 Option 是什么关系？

这里又容易混。

假设我们定义：

文本
Option 1：Color
Option 2：Size

那么：

文本
Color
├── Black
└── White

Size
├── S
├── M
└── L

Shopify 根据这些选项组合出具体 Variant：

文本
Black + S
Black + M
Black + L

White + S
White + M
White + L

所以可以这样理解：

文本
Option
  ↓
提供“选择维度”

Variant
  ↓
一个具体的组合

          ├── Black / S

Option 和 Variant 的数量上限

我的追问09-19 19:15

Shopify对option和变体的数量有限制吗

ChatGPT 讲解09-19 19:15

有，而且这里有一个很重要的版本变化：如果你以前查过 Shopify，可能会看到“最多 3 个 Option、100 个 Variant”的资料——那是旧限制。现在 Shopify 已经提高了 Variant 上限。

现在的限制

截至目前，Shopify 官方文档显示：

项目 当前情况
每个 Product 的 Option 数量 最多 3 个
每个 Product 的 Variant 数量 最多 2,048 个

Shopify 在 2025 年 10 月 15 日将所有商家的 Variant 上限从历史上的 100 提高到了 2,048。ShopifyShopify

不过这里有个容易混淆的地方：Shopify 现在推荐使用新的 GraphQL Product API；旧的 REST Product Variant API 文档仍然显示“3 options / 100 variants”，因为它属于已经 deprecated 的旧模型。Shopify

1. Option 最多 3 个是什么意思？

比如：

文本
Product
└── T-Shirt

可以有：

文本
Option 1：Color
Option 2：Size
Option 3：Material

例如：

文本
Color
├── Black
├── White
└── Red

Size
├── S
├── M
└── L

Material
├── Cotton
└── Polyester

这样理论上的 Variant 数量就是：

文本
3 Colors
× 3 Sizes
× 2 Materials
= 18 Variants

所以：

文本
Color × Size × Material
            ↓
         Variants

2. 2048 个 Variant 是怎么计算的？

这个特别重要。

假设：

文本
Color = 10
Size = 10
Material = 10

那么：

文本
10 × 10 × 10
= 1,000 Variants

没有超过 2,048，所以可以。

但是：

文本
Color = 20
Size = 20
Material = 10

就是：

文本
20 × 20 × 10
= 4,000

这就超过了 Shopify 每个 Product 的 2,048 Variant 限制。Shopify

    </p>
  {% endif %}

  {% if product.metafields.custom.care_instructions.value %}
    <p>
      {{ product.metafields.custom.care_instructions.value }}
    </p>
  {% endif %}

</div>

这里你已经开始在做真正的 Shopify Theme 开发了。

十一、为什么 Size Guide 不一定直接用 Text？

这是非常值得你理解的一个设计问题。

如果你直接：

文本
Size Guide
→ Multi-line text

文本

L: Chest 100cm

但是如果你的商城有 500 个产品：

文本

→ Size Guide A

Product B
→ Size Guide A

Product C
→ Size Guide A

你就不应该把整个 Size Guide 复制到每个 Product。

这时候更好的数据模型可能是：

文本

    ↓
Size Guide
    ↓
Product Metafield
    ↓
Reference

也就是：

文本

   │
   │ size_guide
   ↓

   │
   ├── title
   ├── image
   ├── description
   └── size data

这就是为什么 Shopify 有：

Metafield + Metaobject

这两个概念。

非结构化 Metafield 从哪里来

我的追问09-19 19:22

为什么有的metafield创建出来是unstructed呢

ChatGPT 讲解09-19 19:22

对，这个问题很关键。你看到的 Unstructured（非结构化）Metafield，本质上是 Shopify 对“没有对应 Metafield Definition 的自定义字段”的一种处理方式。

可以把它理解成：

Structured Metafield = 先定义字段，再往字段里填数据。
Unstructured Metafield = 直接存一个自定义字段和值，没有完整的 Definition。

1. 先看两者区别

Structured

你先创建 Definition：

文本
Name: Material
Namespace: custom
Key: material
Type: Single line text

然后 Product：

文本
Classic T-Shirt

Material:
100% Cotton

最终：

文本
Product
└── Metafield Definition
      └── custom.material
             ↓
         "100% Cotton"

这就是比较标准的 Structured Metafield。

Unstructured

以前 Shopify 允许你直接给某个对象添加：

文本
namespace: custom
key: material
value: 100% Cotton

但没有一个完整的 Definition 告诉 Shopify：

文本
这个字段叫什么？
是什么类型？
有哪些验证规则？
是否关联 Metaobject？

于是 Shopify 把它视为：

文本
Unstructured Metafield

2. 为什么会出现 Unstructured？

一个很重要的原因是：

Shopify 历史上的 Metafield 机制发生过演进。

早期 Shopify 的 Metafield 使用方式更加自由。

开发者可以直接使用：

文本
namespace
key
value

例如：

文本
custom.material
=
100% Cotton

并不一定需要先创建 Definition。

后来 Shopify 引入了更加完整的 Metafield Definition 系统。

现在你可以明确告诉 Shopify：

文本
Name:
Material

Namespace:
custom

Key:
material

Type:
Single line text

这样 Shopify 就知道这个字段的结构。

所以你现在看到一些老店铺、老 App 或历史数据里面有：

文本
Unstructured

并不奇怪。

3. 一个非常直观的数据库类比

假设你有一个数据库。

Structured

先定义：

sql
CREATE TABLE products (
    id INT,
    title VARCHAR(255),
    material VARCHAR(255)
);

然后：

文本
Product A
material = "100% Cotton"

这就是结构化。

Unstructured

更像：

json
{
  "id": 1,
  "title": "Classic T-Shirt",
  "custom": {
    "material": "100% Cotton"
  }
}

你虽然存了：

文本
material

但系统没有一个明确的 Schema Definition：

文本
material
→ String
→ 最大长度？
→ 是否必填？
→ 是否关联对象？

所以它更加“自由”。

4. 为什么 Shopify 现在更推荐 Definition？

因为 Definition 可以提供很多额外能力。

例如：

文本
Material
Type:
Single line text

Shopify 就知道：

这个字段只能存文本。

如果是：

文本
Related Product
Type:
Product reference

Shopify 就知道：

这个字段存的是另一个 Product 的引用。

如果是：

文本
Size Guide
Type:
Metaobject reference

Shopify 就知道：

这个字段引用的是一个 Metaobject。

5. 这会直接影响 Theme 开发

比如 Structured Metafield：

文本
custom.size_guide
Type:
Metaobject reference

那么 Liquid 可以根据这个类型访问对应的 Metaobject。

而如果是一个没有 Definition 的老式 Unstructured Metafield：

文本
custom.size_guide
=
"xxx"

Shopify 并不知道：

“xxx”究竟是文本、URL、Product、图片还是 Metaobject。

所以开发体验会差很多。

6. 还有一个非常重要的地方：value

你之前问过：

liquid
product.metafields.custom.material.value

这里现在就很好理解了。

对于一个正常的 Structured Metafield：

文本
Definition
custom.material
Type = Single line text

然后：

文本
Value
100% Cotton

Liquid：

liquid
{{ product.metafields.custom.material.value }}

就是：

文本
100% Cotton

7. 那 Unstructured Metafield 怎么办？

如果你接手一个老 Shopify 项目，发现：

文本
custom.xxx

是 Unstructured，不要马上认为：

“这个字段坏了。”

它可能只是历史遗留数据。

你应该先检查：

文本
Namespace
Key
Value

例如：

文本
namespace = custom
key = material
value = 100% Cotton

然后再判断：

这个字段现在应该是什么数据类型？

如果你确认：

文本
material

就是普通文本，那么可以考虑给它建立一个正式的 Metafield Definition。

8. 你现在作为 Shopify 开发者，应该怎么做？

我建议你的思维方式是：

文本
看到 Unstructured
       ↓
先不要直接修改代码
       ↓
确认 namespace + key
       ↓
确认 value 实际是什么
       ↓
判断应该是什么 Type
       ↓
建立/迁移到 Definition

例如：

文本
Unstructured

custom.material
"100% Cotton"

你判断：

文本
material
↓
Single line text

然后建立：

文本
Definition
custom.material
Type = Single line text

9. 为什么这对你特别重要？

因为以后你做 Shopify 项目，很可能遇到这种情况：

文本
客户：
“我们之前的 Theme 里已经有很多 metafield 了。”

你一看：

文本
custom.xxx
custom.xxx2
custom.xxx3
custom.xxx4

然后发现很多是历史遗留的 Unstructured Metafield。

这时候你不能只看名字。

你需要建立：

文本
数据模型
    ↓
Namespace
    ↓
Key
    ↓
Type
    ↓
Value
    ↓
Theme 如何读取
    ↓
是否需要迁移

这已经属于比较正规的 Shopify 开发思维了。

最后用一句话记住

文本
Structured Metafield
=
Definition + Value
=
“有明确 Schema 的自定义字段”

Unstructured Metafield
=
Namespace + Key + Value
=
“没有正式 Definition 的历史/自由形式字段”

所以你在新项目里，如果没有特殊原因，我建议优先使用 Metafield Definition + 正确的类型，而不是主动设计成 Unstructured。

另外，不要把 Unstructured Metafield 和 Metaobject 混为一谈：

文本
Metafield
= 给 Product 增加一个字段

Metaobject
= 创建一种新的结构化数据对象

Metafield → Metaobject reference
= Product 通过字段引用一个 Metaobject

这个关系弄清楚之后，你后面做 Size Guide、Brand、FAQ、Product Badge、Ingredient、Specification 这些 Shopify 项目会非常顺。
