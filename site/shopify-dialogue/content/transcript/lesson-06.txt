# 第 6 课：Liquid 深入 —— Shopify Theme 的“模板引擎”

这一课非常重要。

如果把你熟悉的 React/Next.js 开发拿来类比：

> **Liquid ≈ Shopify 世界里的模板渲染语言。**

但它和 React 有一个非常大的区别：

> React 主要在浏览器/服务端运行 JavaScript；  
> **Liquid 是 Shopify 在服务器端执行，然后生成 HTML。**

---

## 一、先建立一个最重要的运行模型

你以后看到 Shopify Theme 代码，脑子里应该自动出现：

```text
Shopify 数据
    ↓
Liquid
    ↓
HTML
    ↓
浏览器
    ↓
JavaScript
    ↓
用户交互
```

例如 Shopify 里面有一个 Product：

```text
Product
title = "Classic T-Shirt"
price = $29.99
```

Theme 中：

```liquid
<h1>{{ product.title }}</h1>
```

Shopify 服务器执行 Liquid 后：

```html
<h1>Classic T-Shirt</h1>
```

然后浏览器拿到的是：

```html
<h1>Classic T-Shirt</h1>
```

**浏览器根本不知道 `{{ product.title }}` 是什么。**

这点一定要记住。

---

# 二、Liquid 最核心的 3 种语法

你以后 80% 的 Liquid 代码，基本都可以归到这三类。

### ① 输出数据：`{{ }}`

例如：

```liquid
{{ product.title }}
```

输出：

```text
Classic T-Shirt
```

再比如：

```liquid
{{ product.vendor }}
```

```liquid
{{ product.description }}
```

```liquid
{{ product.price }}
```

---

### ② 执行逻辑：`{% %}`

例如：

```liquid
{% if product.available %}
  <button>Add to cart</button>
{% else %}
  <button disabled>Sold out</button>
{% endif %}
```

这里：

```liquid
{% if ... %}
```

不是输出内容。

它是在告诉 Shopify：

> “判断一下这个商品是否可以买。”

---

### ③ 注释：`{# #}`？

这里要特别注意：

Liquid **不是**：

```liquid
{# comment #}
```

而是：

```liquid
{% comment %}
这是注释
{% endcomment %}
```

---

# 三、Liquid 的变量到底是什么？

比如：

```liquid
{{ product.title }}
```

这里实际上是：

```text
product
  ↓
对象
  ↓
title
```

类似你在 JavaScript 里面：

```js
product.title
```

所以你可以先把它理解成：

```liquid
{{ product.title }}
```

≈

```js
product.title
```

但是两者运行环境完全不同。

---

# 四、Shopify 最重要的对象之一：Product

例如：

```liquid
{{ product.title }}
```

你可以继续访问：

```liquid
{{ product.vendor }}
{{ product.type }}
{{ product.description }}
```

以及：

```liquid
{{ product.variants }}
```

这就是我们上一课讲过的：

```text
Product
   │
   ├── title
   ├── description
   ├── images
   ├── variants
   ├── vendor
   └── ...
```

# 五、Variants 是 Liquid 开发的重点

假设一个 T-Shirt：

```text
Product
└── Classic T-Shirt

Variants
├── Black / S
├── Black / M
├── Black / L
├── White / S
├── White / M
└── White / L
```

Liquid 可以遍历：

```liquid
{% for variant in product.variants %}
  <div>
    {{ variant.title }}
    {{ variant.price }}
  </div>
{% endfor %}
```

结果可能生成：

```html
<div>Black / S $29.99</div>
<div>Black / M $29.99</div>
<div>Black / L $29.99</div>
<div>White / S $29.99</div>
<div>White / M $29.99</div>
<div>White / L $29.99</div>
```

# 六、`for` 循环

这和 JavaScript 非常容易类比。

JS：

```js
products.forEach(product => {
  console.log(product.title)
})
```

Liquid：

```liquid
{% for product in collection.products %}
  {{ product.title }}
{% endfor %}
```

所以你可以形成一个映射：

| JavaScript | Liquid |
|---|---|
| `if` | `{% if %}` |
| `else` | `{% else %}` |
| `forEach` | `{% for %}` |
| `object.property` | `object.property` |
| 输出 | `{{ }}` |

---

# 七、Liquid Filter：非常重要

这是 Shopify 开发和普通模板语言非常不一样的地方。

例如：

```liquid
{{ product.title | upcase }}
```

假设：

```text
Classic T-Shirt
```

结果：

```text
CLASSIC T-SHIRT
```

你可以理解成：

```text
数据
 ↓
filter
 ↓
处理后的数据
```

---

## 常见 Filter

### `upcase`

```liquid
{{ product.title | upcase }}
```

### `downcase`

```liquid
{{ product.title | downcase }}
```

### `escape`

```liquid
{{ product.title | escape }}
```

这个非常重要。

尤其是输出用户输入的数据时。

---

### `default`

```liquid
{{ product.vendor | default: 'Unknown Brand' }}
```

如果 vendor 没有值：

```text
Unknown Brand
```

---

### `money`

价格开发中非常常见：

```liquid
{{ product.price | money }}
```

例如可能显示：

```text
$29.99
```

---

### `image_url`

例如：

```liquid
{{ product.featured_image | image_url: width: 800 }}
```

告诉 Shopify：

> 给我这个图片，并生成适合 800px 宽度的 URL。

---

# 八、Filter 可以连续使用

这也是很常见的写法：

```liquid
{{ product.title | downcase | escape }}
```

执行过程可以理解成：

```text
product.title
      ↓
downcase
      ↓
escape
      ↓
输出
```

类似：

```js
escape(downcase(product.title))
```

# 九、Liquid 的条件判断

例如商品是否有库存：

```liquid
{% if product.available %}
  <button>Add to cart</button>
{% else %}
  <button disabled>
    Sold out
  </button>
{% endif %}
```

这就是一个非常典型的 Shopify 商品组件。

最终用户看到：

### 有库存

```text
[ Add to cart ]
```

### 没库存

```text
[ Sold out ]
```

# 十、还有一个非常重要的概念：对象可能为空

比如：

```liquid
{% if product.metafields.custom.material %}
  <p>
    Material:
    {{ product.metafields.custom.material }}
  </p>
{% endif %}
```

这里就是：

```text
有没有 Material？
       ↓
     有？
   ↙     ↘
 YES      NO
 ↓         ↓
显示      不显示
```

以后做：

- Metafield
- Metaobject
- 产品自定义字段
- Banner
- Size Guide
- Brand
- FAQ

都会大量用到这种判断。

# 十一、一个真实的 Product Card

现在我们把前面的东西组合起来。

```liquid
<div class="product-card">

  {% if product.featured_image %}
    <img
      src="{{ product.featured_image | image_url: width: 500 }}"
      alt="{{ product.title | escape }}"
    >
  {% endif %}

  <h3>
    {{ product.title }}
  </h3>

  <p>
    {{ product.price | money }}
  </p>

  {% if product.available %}
    <a href="{{ product.url }}">
      View product
    </a>
  {% else %}
    <span>
      Sold out
    </span>
  {% endif %}

</div>
```

你现在应该能读懂绝大部分代码。

# 十二、注意：Liquid 不负责真正的“点击交互”

这是 Shopify 初学者最容易混淆的地方。

比如：

```liquid
<button>Add to cart</button>
```

Liquid 可以：

> **生成这个按钮。**

但是用户点击：

```text
点击 Add to cart
        ↓
发生什么？
```

通常需要：

```text
JavaScript
    ↓
Cart API
    ↓
Shopify Cart
    ↓
返回 JSON
    ↓
更新 Cart Drawer
```

所以：

### Liquid

负责：

```text
“页面长什么样”
```

### JavaScript

负责：

```text
“用户操作以后发生什么”
```

这就是我们前面讲的两个世界。

# 十三、一个非常重要的工程思维

假设产品经理说：

> “商品页增加一个 Add to Cart 按钮，点击以后不要刷新页面，右侧弹出购物车。”

千万不要只想到：

```text
写一个 button
```

你应该马上拆成：

```text
1. Liquid
   ↓
   生成商品信息

2. Variant
   ↓
   确定用户购买哪个 SKU

3. Button
   ↓
   Add to Cart

4. JavaScript
   ↓
   监听点击

5. Cart API
   ↓
   添加 Variant

6. 返回 Cart 数据
   ↓
   
7. 更新 Cart Drawer
   ↓

8. DOM 更新
```

这才是 Shopify 前端开发的思维。

# 十四、今天再认识一个非常重要的对象：`section`

上一课我们讲过：

```text
Template
   ↓
Section
   ↓
Liquid
   ↓
HTML
```

现在结合 Liquid：

例如：

```text
templates/product.json
```

决定：

```text
Product Page
    ↓
main-product
    ↓
main-product.liquid
```

然后：

```liquid
{{ product.title }}
```

拿到当前商品。

所以你可以理解：

> **Template 决定“用哪个页面结构”，Section 决定“页面有哪些模块”，Liquid 决定“模块如何渲染数据”。**

# 十五、把它和 React 对比一下

作为前端开发，你可以这样记：

### React

```jsx
function ProductCard({ product }) {
  return (
    <div>
      <h2>{product.title}</h2>
      <p>{product.price}</p>
    </div>
  )
}
```

### Shopify Liquid

```liquid
<div>
  <h2>{{ product.title }}</h2>
  <p>{{ product.price | money }}</p>
</div>
```

概念非常接近：

```text
React Props
      ↓
  product

Liquid Context
      ↓
  product
```

但是：

```text
React
↓
JavaScript runtime

Liquid
↓
Shopify server rendering
```

这是你必须建立起来的区别。

麻烦你再给我解释下产品变体的概念

## ChatGPT · 2026-09-19 Sat 19:14

当然可以。**Product Variant（产品变体）是 Shopify 里非常核心的概念**，而且它和普通前端开发里的“商品属性”有一点区别。

你可以先记住一句话：

> **Product 是“卖什么”，Variant 是“具体卖哪一个”。**

---

## 1. 用最直观的例子理解

假设你在 Shopify 卖一件 T 恤：

**Product：**

> Classic T-Shirt

但是这件 T 恤有：

- 黑色 / S
- 黑色 / M
- 黑色 / L
- 白色 / S
- 白色 / M
- 白色 / L

那么：

```text
Product
└── Classic T-Shirt
      │
      ├── Variant 1：Black / S
      ├── Variant 2：Black / M
      ├── Variant 3：Black / L
      ├── Variant 4：White / S
      ├── Variant 5：White / M
      └── Variant 6：White / L
```

这里：

**Classic T-Shirt 是 Product**

而：

**Black / M 是一个 Variant**

---

# 2. 为什么 Shopify 要把 Product 和 Variant 分开？

因为消费者看到的是：

> 我要买一件 T-Shirt。

但是仓库真正需要知道的是：

> 我要发 **黑色、M码** 的这一件。

所以：

```text
Product
= 商品概念
```

而：

```text
Variant
= 可以被单独购买、库存管理的具体规格
```

例如：

| Product | Variant | SKU | 库存 |
|---|---|---|---:|
| Classic T-Shirt | Black / S | TS-BLK-S | 20 |
| Classic T-Shirt | Black / M | TS-BLK-M | 15 |
| Classic T-Shirt | Black / L | TS-BLK-L | 8 |
| Classic T-Shirt | White / S | TS-WHT-S | 12 |
| Classic T-Shirt | White / M | TS-WHT-M | 25 |

这里你就能看到一个非常重要的事情：

**库存不是简单地属于 Product，而是和具体 Variant 相关。**

---

# 3. Variant 和 Option 是什么关系？

这里又容易混。

假设我们定义：

```text
Option 1：Color
Option 2：Size
```

那么：

```text
Color
├── Black
└── White

Size
├── S
├── M
└── L
```

Shopify 根据这些选项组合出具体 Variant：

```text
Black + S
Black + M
Black + L

White + S
White + M
White + L
```

所以可以这样理解：

```text
Option
  ↓
提供“选择维度”

Variant
  ↓
一个具体的组合
```

---

# 4. 用前端开发的思维理解

这个概念其实非常适合用你熟悉的前端思维理解。

假设：

```js
const product = {
  title: "Classic T-Shirt",
  options: [
    {
      name: "Color",
      values: ["Black", "White"]
    },
    {
      name: "Size",
      values: ["S", "M", "L"]
    }
  ]
}
```

那么 Variant 可以理解成：

```js
const variants = [
  {
    id: 101,
    options: ["Black", "S"],
    price: 29.99,
    sku: "TS-BLK-S"
  },
  {
    id: 102,
    options: ["Black", "M"],
    price: 29.99,
    sku: "TS-BLK-M"
  },
  {
    id: 103,
    options: ["Black", "L"],
    price: 29.99,
    sku: "TS-BLK-L"
  }
]
```

所以：

```text
Product
   │
   ├── Options
   │      ├── Color
   │      └── Size
   │
   └── Variants
          ├── Black / S
          ├── Black / M
          └── Black / L
```

---

# 5. 为什么前端开发特别需要理解 Variant？

因为商品详情页通常不是：

```text
价格
+
Add to Cart
```

而是：

```text
Classic T-Shirt

Color
○ Black
○ White

Size
○ S
○ M
○ L

$29.99

[ Add to Cart ]
```

用户选择：

```text
Black
+
M
```

前端需要找到：

```text
Black / M
```

对应的 Variant ID。

然后加入购物车的其实不是：

```text
Product ID
```

而通常是：

```text
Variant ID
```

这点**非常重要**。

# 6. 举一个完整的购物流程

用户进入：

```text
Classic T-Shirt
```

Shopify：

```text
Product
   ↓
Classic T-Shirt
```

用户选择：

```text
Color = Black
Size = M
```

前端找到：

```text
Variant
Black / M
ID = 123456
```

然后点击：

```text
Add to Cart
```

前端实际上是在告诉 Shopify：

```text
我要购买 Variant ID = 123456
数量 = 1
```

然后：

```text
Variant
   ↓
Cart
   ↓
Checkout
   ↓
Order
```

所以你之前学的：

```text
Product → Variant → Cart → Checkout → Order
```

现在应该更容易理解了。

---

# 7. 为什么不能直接把 Product 放进购物车？

因为 Shopify 必须知道你买的是哪一个具体规格。

例如：

```text
Product:
iPhone Case
```

如果有：

```text
Black / iPhone 17
Black / iPhone 17 Pro
White / iPhone 17
White / iPhone 17 Pro
```

用户说：

> 我要买 iPhone Case。

这还不够。

Shopify 必须知道：

> **哪个 Variant？**

例如：

```text
White / iPhone 17 Pro
```

因为这个 Variant 可能拥有自己的：

- SKU
- 库存
- 价格
- 图片
- 条码
- 配送信息

---

# 8. Product 和 Variant 最重要的区别

你可以记这个表：

| | Product | Variant |
|---|---|---|
| 含义 | 商品整体 | 商品具体规格 |
| 示例 | Classic T-Shirt | Black / M |
| 商品标题 | ✅ | 通常继承/关联 |
| 规格组合 | ❌ | ✅ |
| SKU | 通常不是核心承载 | ✅ |
| 库存 | 通常通过变体管理 | ✅ |
| 具体购买对象 | ❌ | ✅ |
| Add to Cart | ❌ | **通常加入 Variant** |

---

# 9. 一个非常容易犯的错误

以后你写 Shopify 商品页时，千万不要想成：

```text
用户选择颜色
    ↓
修改 Product
```

正确的思维是：

```text
Product
   ↓
多个 Variant

用户选择 Color / Size
   ↓
找到对应 Variant
   ↓
拿到 Variant ID
   ↓
Add to Cart
```

也就是说：

> **用户选择规格，本质上是在“选择 Variant”。**

---

# 10. 再用一个你更熟悉的类比

把 Product 想成一个 React 页面：

```text
Product
= 商品详情页对应的“整体数据”
```

把 Variant 想成这个商品真正可以购买的一个 SKU：

```text
Variant
= 一个具体的可购买 SKU
```

例如：

```text
Nike Air Max 运动鞋
        ↓
Product
        ↓
────────────────────
Black / 42
Black / 43
Black / 44
White / 42
White / 43
White / 44
────────────────────
        ↓
     Variants
```

所以以后你看到：

```liquid
product.variants
```

脑子里就应该马上想到：

> **这个 Product 底下所有可以购买的具体规格。**

而：

```liquid
variant.id
```

就是：

> **这个具体规格在 Shopify 里的身份 ID。**

| **每个 Product 的 Option 数量** | **最多 3 个** |
| **每个 Product 的 Variant 数量** | **最多 2,048 个** |

Shopify 在 **2025 年 10 月 15 日**将所有商家的 Variant 上限从历史上的 100 提高到了 **2,048**。 [The product variant limit is now 2048 for all merchants - Shopify developer changelog](https://shopify.dev/changelog/the-product-variant-limit-is-now-2048-for-all-merchants?utm_source=chatgpt.com) [ProductVariant - GraphQL Admin](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/ProductVariant?utm_source=chatgpt.com)

不过这里有个容易混淆的地方：Shopify 现在推荐使用新的 **GraphQL Product API**；旧的 REST Product Variant API 文档仍然显示“3 options / 100 variants”，因为它属于已经 deprecated 的旧模型。 [Product Variant](https://shopify.dev/docs/api/admin-rest/latest/resources/product-variant?utm_source=chatgpt.com)

## 1. Option 最多 3 个是什么意思？

比如：

```text
Product
└── T-Shirt
```

可以有：

```text
Option 1：Color
Option 2：Size
Option 3：Material
```

例如：

```text
Color
├── Black
├── White
└── Red

Size
├── S
├── M
└── L

Material
├── Cotton
└── Polyester
```

这样理论上的 Variant 数量就是：

```text
3 Colors
× 3 Sizes
× 2 Materials
= 18 Variants
```

所以：

```text
Color × Size × Material
            ↓
         Variants
```

## 2. 2048 个 Variant 是怎么计算的？

这个特别重要。

假设：

```text
Color = 10
Size = 10
Material = 10
```

那么：

```text
10 × 10 × 10
= 1,000 Variants
```

没有超过 2,048，所以可以。

但是：

```text
Color = 20
Size = 20
Material = 10
```

就是：

```text
20 × 20 × 10
= 4,000
```

这就超过了 Shopify 每个 Product 的 2,048 Variant 限制。 [Product - GraphQL Admin](https://shopify.dev/docs/api/admin-graphql/latest/objects/product?utm_source=chatgpt.com)

```text

       ↓

```

这就是 Shopify Theme 前端开发中非常重要的一块。

# 4. 一个非常重要的设计问题

假设你的产品有：

```text

Size：S / M / L
Material：Cotton / Polyester
```

理论上：

```text

```

所以最多 12 个组合。

```text

Black / M / Cotton
Black / L / Cotton

White / S / Polyester
White / M / Polyester
```

也就是说：

> **Option 的组合空间 ≠ 实际存在的 Variant 数量。**

> **Shopify 自带 Product 字段不够用时，就通过 Metafield 给 Product 增加自己的字段。**

比如 Shopify 原生有：

```text
Product
├── title
├── description
├── vendor
├── variants
└── ...
```

你想再增加：

```text
Material
Size Guide
Care Instructions
Brand Story
Video
```

就可以用 Metafield。

# 一、先看最终效果

假设我们想给每个 Product 增加：

```text
Material
```

例如：

```text
Classic T-Shirt

Material:
100% Cotton
```

那么我们可以创建一个 Product Metafield：

```text
Namespace: custom
Key: material
Type: Single line text
```

然后给某个产品填写：

```text
Value:
100% Cotton
```

最终 Liquid 就可以：

```liquid
{{ product.metafields.custom.material.value }}
```

输出：

```text
100% Cotton
```

---

# 二、第一步：创建 Metafield Definition

这里有一个非常重要的概念：

> **Definition 和 Value 不是一回事。**

你可以把它理解成数据库：

### Definition

相当于：

```text
数据库字段定义
```

例如：

```text
字段名：Material
类型：文本
```

### Value

相当于：

```text
某一条 Product 记录的具体值
```

例如：

```text
Product A → 100% Cotton
Product B → 80% Cotton / 20% Polyester
```

所以：

```text
Metafield Definition
        ↓
定义“这个字段是什么”
        ↓
Product
        ↓
填写具体 Value
```

进入 Shopify 后台：

```text

   ↓
Custom data
   ↓
Products
```

然后：

```text
Add definition
```

创建一个新的 Product Metafield。

例如：

```text
Name:
Material
```

Namespace 和 Key 可以是：

```text
custom.material
```

类型选择：

```text
Single line text
```

然后保存。

# 四、创建完成后是什么样？

你现在实际上定义了一个新的 Product 字段：

```text
Product
│
├── Shopify 原生字段
│     ├── title
│     ├── description
│     ├── vendor
│     └── variants
│
└── Custom fields
      └── Material
```

也就是：

```text
product.metafields.custom.material
```

# 五、第二步：给产品填写值

然后进入：

```text
Products
   ↓
Classic T-Shirt
```

在 Product 编辑页面里，你会看到刚才创建的：

```text

[                    ]
```

填写：

```text

```

保存。

现在：

```text

```

```text
custom.material

```

# 六、第三步：Liquid 读取

在 Theme 里面：

```liquid
{{ product.metafields.custom.material.value }}
```

输出：

```text
100% Cotton
```

这里我建议你养成一个习惯：

```liquid
.value
```

因为 Metafield 本身是一个 Metafield 对象，而 `.value` 才是它存储的实际值。Shopify 的 Liquid Metafield 对象提供 `value` 属性来获取实际数据。 [Liquid objects: metafield](https://shopify.dev/docs/api/liquid/objects/metafield)

也可能看到：


对于现代 Shopify Theme 开发，我建议你明确写：


因为这样语义更加清楚：

```text

 ↓
```

# 八、如果是图片呢？

所以 Metafield 的 Type 很重要。

# 十、一个真实的 Shopify 项目例子

假设你的客户说：

> “我们商品详情页下面需要显示 Material、Care Instructions 和 Size Guide。”

你可能设计：

```text
Product
│
├── Material
│     └── Single line text
│
├── Care Instructions
│     └── Multi-line text
│
└── Size Guide
      └── Metaobject reference
```

那么 Liquid：

```liquid
<div class="product-info">

  {% if product.metafields.custom.material.value %}
    <p>
      Material:
      {{ product.metafields.custom.material.value }}
    </p>
  {% endif %}

  {% if product.metafields.custom.care_instructions.value %}
    <p>
      {{ product.metafields.custom.care_instructions.value }}
    </p>
  {% endif %}

</div>
```

这里你已经开始在做真正的 Shopify Theme 开发了。

# 十一、为什么 Size Guide 不一定直接用 Text？

这是非常值得你理解的一个设计问题。

如果你直接：

```text
Size Guide
→ Multi-line text
```

可能写成：

```text
S: Chest 90cm
M: Chest 95cm
L: Chest 100cm
```

但是如果你的商城有 500 个产品：

```text
Product A
→ Size Guide A

Product B
→ Size Guide A

Product C
→ Size Guide A
```

你就不应该把整个 Size Guide 复制到每个 Product。

这时候更好的数据模型可能是：

```text
Metaobject
    ↓
Size Guide
    ↓
Product Metafield
    ↓
Reference
```

也就是：

```text
Product
   │
   │ size_guide
   ↓
Size Guide Metaobject
   │
   ├── title
   ├── image
   ├── description
   └── size data
```

这就是为什么 Shopify 有：

> **Metafield + Metaobject**

这两个概念。


所以：

## 我的提问 · 2026-09-19 Sat 19:22

为什么有的metafield创建出来是unstructed呢

## ChatGPT · 2026-09-19 Sat 19:22

对，这个问题很关键。你看到的 **Unstructured（非结构化）Metafield**，本质上是 Shopify 对“没有对应 Metafield Definition 的自定义字段”的一种处理方式。

可以把它理解成：

> **Structured Metafield = 先定义字段，再往字段里填数据。**  
> **Unstructured Metafield = 直接存一个自定义字段和值，没有完整的 Definition。**

---

## 1. 先看两者区别

### Structured

你先创建 Definition：

```text
Name: Material
Namespace: custom
Key: material
Type: Single line text
```

然后 Product：

```text
Classic T-Shirt

Material:
100% Cotton
```

最终：

```text
Product
└── Metafield Definition
      └── custom.material
             ↓
         "100% Cotton"
```

这就是比较标准的 **Structured Metafield**。

---

### Unstructured

以前 Shopify 允许你直接给某个对象添加：

```text
namespace: custom
key: material
value: 100% Cotton
```

但没有一个完整的 Definition 告诉 Shopify：

```text
这个字段叫什么？
是什么类型？
有哪些验证规则？
是否关联 Metaobject？
```

于是 Shopify 把它视为：

```text
Unstructured Metafield
```

---

# 2. 为什么会出现 Unstructured？

一个很重要的原因是：

### Shopify 历史上的 Metafield 机制发生过演进。

早期 Shopify 的 Metafield 使用方式更加自由。

开发者可以直接使用：

```text
namespace
key
value
```

例如：

```text
custom.material
=
100% Cotton
```

并不一定需要先创建 Definition。

后来 Shopify 引入了更加完整的 **Metafield Definition** 系统。

现在你可以明确告诉 Shopify：

```text
Name:
Material

Namespace:
custom

Key:
material

Type:
Single line text
```

这样 Shopify 就知道这个字段的结构。

所以你现在看到一些老店铺、老 App 或历史数据里面有：

```text
Unstructured
```

并不奇怪。

---

# 3. 一个非常直观的数据库类比

假设你有一个数据库。

### Structured

先定义：

```sql
CREATE TABLE products (
    id INT,
    title VARCHAR(255),
    material VARCHAR(255)
);
```

然后：

```text
Product A
material = "100% Cotton"
```

这就是结构化。

---

### Unstructured

更像：

```json
{
  "id": 1,
  "title": "Classic T-Shirt",
  "custom": {
    "material": "100% Cotton"
  }
}
```

你虽然存了：

```text
material
```

但系统没有一个明确的 Schema Definition：

```text
material
→ String
→ 最大长度？
→ 是否必填？
→ 是否关联对象？
```

所以它更加“自由”。

---

# 4. 为什么 Shopify 现在更推荐 Definition？

因为 Definition 可以提供很多额外能力。

例如：

```text
Material
Type:
Single line text
```

Shopify 就知道：

> 这个字段只能存文本。

如果是：

```text
Related Product
Type:
Product reference
```

Shopify 就知道：

> 这个字段存的是另一个 Product 的引用。

如果是：

```text
Size Guide
Type:
Metaobject reference
```

Shopify 就知道：

> 这个字段引用的是一个 Metaobject。

---

# 5. 这会直接影响 Theme 开发

比如 Structured Metafield：

```text
custom.size_guide
Type:
Metaobject reference
```

那么 Liquid 可以根据这个类型访问对应的 Metaobject。

而如果是一个没有 Definition 的老式 Unstructured Metafield：

```text
custom.size_guide
=
"xxx"
```

Shopify 并不知道：

> “xxx”究竟是文本、URL、Product、图片还是 Metaobject。

所以开发体验会差很多。

---

# 6. 还有一个非常重要的地方：`value`

你之前问过：

```liquid
product.metafields.custom.material.value
```

这里现在就很好理解了。

对于一个正常的 Structured Metafield：

```text
Definition
custom.material
Type = Single line text
```

然后：

```text
Value
100% Cotton
```

Liquid：

```liquid
{{ product.metafields.custom.material.value }}
```

就是：

```text
100% Cotton
```

---

# 7. 那 Unstructured Metafield 怎么办？

如果你接手一个老 Shopify 项目，发现：

```text
custom.xxx
```

是 Unstructured，不要马上认为：

> “这个字段坏了。”

它可能只是历史遗留数据。

你应该先检查：

```text
Namespace
Key
Value
```

例如：

```text
namespace = custom
key = material
value = 100% Cotton
```

然后再判断：

> 这个字段现在应该是什么数据类型？

如果你确认：

```text
material
```

就是普通文本，那么可以考虑给它建立一个正式的 Metafield Definition。

---

# 8. 你现在作为 Shopify 开发者，应该怎么做？

我建议你的思维方式是：

```text
看到 Unstructured
       ↓
先不要直接修改代码
       ↓
确认 namespace + key
       ↓
确认 value 实际是什么
       ↓
判断应该是什么 Type
       ↓
建立/迁移到 Definition
```

例如：

```text
Unstructured

custom.material
"100% Cotton"
```

你判断：

```text
material
↓
Single line text
```

然后建立：

```text
Definition
custom.material
Type = Single line text
```

---

# 9. 为什么这对你特别重要？

因为以后你做 Shopify 项目，很可能遇到这种情况：

```text
客户：
“我们之前的 Theme 里已经有很多 metafield 了。”
```

你一看：

```text
custom.xxx
custom.xxx2
custom.xxx3
custom.xxx4
```

然后发现很多是历史遗留的 Unstructured Metafield。

这时候你不能只看名字。

你需要建立：

```text
数据模型
    ↓
Namespace
    ↓
Key
    ↓
Type
    ↓
Value
    ↓
Theme 如何读取
    ↓
是否需要迁移
```

这已经属于比较正规的 Shopify 开发思维了。

---

## 最后用一句话记住

```text
Structured Metafield
=
Definition + Value
=
“有明确 Schema 的自定义字段”

Unstructured Metafield
=
Namespace + Key + Value
=
“没有正式 Definition 的历史/自由形式字段”
```

所以你在**新项目**里，如果没有特殊原因，我建议优先使用 **Metafield Definition + 正确的类型**，而不是主动设计成 Unstructured。

另外，**不要把 Unstructured Metafield 和 Metaobject 混为一谈**：

```text
Metafield
= 给 Product 增加一个字段

Metaobject
= 创建一种新的结构化数据对象

Metafield → Metaobject reference
= Product 通过字段引用一个 Metaobject
```

这个关系弄清楚之后，你后面做 **Size Guide、Brand、FAQ、Product Badge、Ingredient、Specification** 这些 Shopify 项目会非常顺。
