上一课，我们学习了 Lighthouse、axe-core、WAVE 以及 Chrome DevTools 无障碍调试。

这一课，我们将真正站在使用辅助技术的用户角度访问网站，学习如何进行人工无障碍测试。

对于 Shopify Theme 开发工程师而言，这项能力非常重要。因为即使网站的 Lighthouse Accessibility 达到 100 分，axe-core 没有发现任何违规，用户仍然可能无法选择商品、修改购物车或者完成购买。

本课将按照测试环境搭建、键盘测试、屏幕阅读器操作、视觉辅助测试、Shopify 完整购买流程测试以及问题修复的顺序展开。

人工测试与自动化检测最大的区别是：它不仅检查元素是否具有正确的属性，还要检查用户是否能够理解信息、找到操作入口，并最终完成任务。

例如 Cart Drawer：

| 检查项目 | 自动检测 | 人工测试 |
|---|---|---|
| 是否具有 dialog 角色 | 可以 | 可以 |
| Dialog 是否具有名称 | 可以 | 可以 |
| 打开后焦点是否合理 | 有限 | 可以 |
| 是否能够通过 Esc 关闭 | 通常不能完整验证 | 可以 |
| 删除商品后焦点是否合理 | 通常不能 | 可以 |
| 关闭后是否恢复焦点 | 通常不能 | 可以 |
| 是否能够独立完成购买 | 不能完整判断 | 可以 |

**人工测试的核心不是检查 ARIA，而是验证用户能否使用网站。**

## 3. Keyboard Only：仅使用键盘测试

在开启屏幕阅读器之前，建议先关闭屏幕阅读器，单独进行键盘测试。

因为并非所有需要键盘操作的用户都使用屏幕阅读器。

### 3.1 常用测试按键

| 按键 | 测试用途 |
|---|---|
| Tab | 下一个常规可聚焦元素 |
| Shift + Tab | 上一个常规可聚焦元素 |
| Enter | 激活链接或按钮、提交表单 |
| Space | 激活按钮、切换 Checkbox |
| Esc | 退出适用的弹窗、菜单 |
| Arrow Keys | Radio、Select、Tabs 等内部导航 |
| Home / End | 部分复合组件的首尾导航 |
| PageUp / PageDown | 页面滚动、部分数值控件 |

注意，不同组件具有不同的键盘交互模型，并不是所有组件都应该支持上述全部按键。

在真实网站中，需要观察焦点顺序是否符合内容和业务逻辑，而不是只判断所有按钮能不能获得焦点。

### 3.3 键盘测试中的典型错误

| 问题 | 可能原因 |
|---|---|
| 按 Tab 完全找不到某个按钮 | 使用 div + click |
| 焦点存在但视觉上看不到 | `outline: none` |
| 焦点进入关闭的 Drawer | 仅使用 transform 隐藏 |
| 焦点顺序与内容逻辑不一致 | CSS order 或正数 tabindex |
| Enter 正常但 Space 无效 | 自定义 button 行为不完整 |
| 打开 Modal 后仍能进入背景 | 缺少模态隔离 |
| 删除商品后焦点回到 body | 原焦点节点被销毁 |
| 焦点被 Sticky Header 完全遮挡 | 缺少滚动空间 |

其中 WCAG 2.4.11 Focus Not Obscured（Minimum）要求获得键盘焦点的组件不能被作者创建的内容完全遮挡。<Cite ref="turn266530search8"/>

### 3.4 Console 焦点调试工具

以后测试复杂 Shopify 组件时，可以直接在 Console 中执行：

```javascript
window.stopFocusDebug?.();

const controller = new AbortController();

document.addEventListener('focusin', event => {
  console.log('Focus in:', event.target);
}, {
  signal: controller.signal,
  capture: true
});

document.addEventListener('focusout', event => {
  console.log('Focus out:', {
    from: event.target,
    to: event.relatedTarget
  });
}, {
  signal: controller.signal,
  capture: true
});

window.stopFocusDebug = () => controller.abort();
```

结束检测时：

```javascript
stopFocusDebug();
```

这个工具尤其适合排查 Section Rendering、Cart Drawer、Quick Add Modal 中的焦点异常。

但它只能监控 DOM Focus，无法直接监控屏幕阅读器的虚拟光标。

## 4. NVDA：安装、配置与实际使用

NVDA 是 Windows 前端开发人员非常实用的屏幕阅读器测试工具。

### 4.1 安装与启动

从 [NV Access 官网](https://www.nvaccess.org/download/) 下载并安装。

NVDA 的很多快捷键需要使用 NVDA Modifier Key，通常是 Insert，也可以配置为 Caps Lock。

例如：

```text
NVDA + F7
```

在使用 Insert 作为 Modifier 时，就表示 Insert + F7。

### 4.2 Speech Viewer：非常重要的调试功能

开启 NVDA 后：

```text
NVDA + N
    → Tools
        → Speech Viewer
```

Speech Viewer 可以用文字显示 NVDA 的语音输出，方便开发人员复制、分析和记录播报结果。<Cite ref="turn266530search0"/>

## 5. Browse Mode 与 Focus Mode 深入理解

第 2 课介绍过这两个概念，现在从实际操作层面理解它们。

### 5.1 Browse Mode（浏览模式）

在 Browse Mode 中，NVDA 使用自身的文档表示浏览网页内容。

用户不需要每次都按 Tab，可以通过快捷键快速查找标题、表单、链接、按钮等元素。

例如按 H，跳到下一个标题。

这个过程中，屏幕阅读器的阅读位置不一定等于 `document.activeElement`。

### 5.2 Focus Mode（焦点模式）

当用户需要在输入框中输入内容，或者操作需要接收按键的组件时，NVDA 会在适用情况下自动进入 Focus Mode。

此时普通按键通常会被传递给网页控件，而不是作为 NVDA 的单字母导航命令。<Cite ref="turn266530search0"/>

### 5.3 NVDA 常用快捷键速查表

| 快捷键 | 功能 |
|---|---|
| NVDA + Space | 切换 Browse / Focus Mode |
| NVDA + F7 | 打开 Elements List |
| NVDA + Tab | 报告当前焦点 |
| H / Shift + H | 下一个 / 上一个标题 |
| 1～6 | 跳转至对应级别标题 |
| K | 下一个链接 |
| B | 下一个按钮 |
| F | 下一个表单字段 |
| E | 下一个编辑框 |
| X | 下一个 Checkbox |
| R | 下一个 Radio Button |
| C | 下一个 Combobox |
| G | 下一个图形 |
| D | 下一个 Landmark |
| T | 下一个表格 |
| NVDA + Q | 退出 NVDA |

单字母导航通常在 Browse Mode 下使用，Shift + 对应字母可以反向查找。完整命令以 [NVDA 官方快捷键手册](https://download.nvaccess.org/documentation/en/keyCommands.html) 为准。<Cite ref="turn280440search6"/>

### 5.4 为什么这个知识对前端开发特别重要？

假设我们错误地实现了一个自定义 Combobox：

```html
<div
  tabindex="0"
  class="custom-select"
>
  Select size
</div>
```

即使开发者监听了所有 keydown 事件，屏幕阅读器仍然可能无法正确识别它属于什么控件，也可能无法在预期时机将按键传递给组件。

因此，正确的 Role 不只是影响播报文字，还会影响辅助技术如何与组件进行交互。

```text

Quick add
Quick add

```

## 7. VoiceOver：苹果设备无障碍测试

VoiceOver 与 NVDA 的导航机制存在一定差异，因此不能认为 NVDA 测试通过，VoiceOver 就一定没有问题。

### 7.1 macOS VoiceOver 常用快捷键

macOS 可以通过 Command + F5 开启或关闭 VoiceOver，部分设备或键盘配置可能需要使用 Fn。

VO 表示 VoiceOver Modifier，通常是 Control + Option，也可以配置为 Caps Lock。

| 快捷键 | 功能 |
|---|---|
| Command + F5 | 开启或关闭 VoiceOver |
| VO + Right Arrow | 下一个项目 |
| VO + Left Arrow | 上一个项目 |
| VO + Space | 激活当前项目 |
| VO + U | 打开 Rotor |
| VO + Shift + Down Arrow | 与当前区域交互 |
| VO + Shift + Up Arrow | 停止与当前区域交互 |

Rotor 类似于 NVDA 的 Elements List，可以帮助用户按照标题、链接、表单控件等分类浏览网页。<Cite ref="turn280440search2"/>

### 7.2 iPhone 如何开启 VoiceOver？

直接在 iPhone 上操作：

**设置 → 辅助功能 → VoiceOver → 开启**

建议同时在「辅助功能快捷键」中配置 VoiceOver。这样就可以通过连续按三次侧边按钮，快速开启或关闭该功能。

开启后，普通触屏操作方式会发生变化。

## 8. Accessible Name 的实际播报测试

假设你正在测试 Collection 页面中的 Quick Add 按钮。

下面三种实现都具有名称，但实际质量并不相同。

<box border radius="lg" padding={3} gap={3}>
  {#each [{label:"Quick add",speech:"Quick add, button",desc:"具有基础名称，但缺少商品上下文。"},{label:"Quick add",speech:"Cotton T-shirt, button",desc:"缺少 Quick add 操作含义，也可能违反 Label in Name。"},{label:"Quick add",speech:"Quick add: Cotton T-shirt, button",desc:"同时表达操作用途和对应商品。"}] as p,i}
    <box gap={2}>
      <box border radius="sm" padding={2} align="center">{p.label}</box>
      <row align="start">
        <icon name="volume-2" size="sm"/>
        <box flex={1} gap={1}>
          <text size="sm" weight="medium">{p.speech}</text>
          <caption>{p.desc}</caption>
        </box>

    </box>
    {#if i<2}<divider/>{/if}
  {/each}
</box>

检测时，不仅要确认有 Accessible Name，还应确认名称能够让用户理解操作。

### 8.1 屏幕阅读器播报的六个检查维度

| 维度 | 示例 |
|---|---|
| Name | Color: Black |
| Role | Radio button |
| State | Checked |
| Value | Quantity: 2 |
| Description | Minimum purchase quantity is 1 |
| Context | Color, grouping |

并不是所有元素都需要具备以上六项信息。具体需要哪些信息，取决于元素角色及业务用途。

### 8.2 不要追求所有屏幕阅读器逐字播报一致

例如同一个 Radio：

```html
<label>
  <input type="radio" name="color" checked>
  Black
</label>
```

不同辅助技术可能播报：

```text
Black, radio button, checked.
```

或者：

```text
Black, selected, radio button.
```

这不一定是兼容性问题。

我们真正需要验证的是：用户是否能够理解 Black 是一个单选控件，以及它当前是否被选中。

**无障碍测试应验证语义与操作结果，而不是强制匹配某一句固定的语音文本。**

## 9. Live Region 不播报的排查方法

这是 Shopify 动态组件中非常常见的问题。

假设加购成功后，视觉上已经显示 Added to cart，但是 NVDA 没有播报。

应该如何排查？

<box border radius="lg" padding={3} gap={1}>
  {#each [{t:"检查业务状态",d:"服务器是否真正返回加购成功？"},{t:"检查 DOM 更新",d:"Live Region 的 textContent 是否发生变化？"},{t:"检查节点生命周期",d:"是否在 Section Rendering 中重新创建了通知节点？"},{t:"检查无障碍树",d:"节点是否位于 hidden、inert 或模态背景中？"},{t:"检查 ARIA 属性",d:"aria-live、role、aria-busy 是否正确？"},{t:"检查通知时机",d:"是否更新过快、文字完全相同或被其他播报覆盖？"},{t:"真实辅助技术验证",d:"分别使用 NVDA 和 VoiceOver 复测。"}] as p,i}
    <box border radius="md" padding={2} gap={1}>**{i+1}. {p.t}**<caption>{p.d}</caption></box>
    {#if i<6}<box align="center"><icon name="arrow-down" size="sm" color="secondary"/></box>{/if}
  {/each}
</box>

### 9.1 错误案例：动态创建已有内容的 Live Region

```javascript
const status = document.createElement('div');

status.setAttribute('role', 'status');

status.textContent = 'Item added to cart.';

document.body.append(status);
```

某些浏览器与屏幕阅读器组合可能不会主动播报这条信息，因为 Live Region 出现时已经包含了内容。

更稳妥的方案是提前在页面中建立空的通知节点。

```html
<p
  id="CartStatus"
  role="status"
  class="visually-hidden"
></p>
```

加购成功之后再更新：

```javascript
document.querySelector('#CartStatus').textContent =
  'Cotton T-shirt added to your cart.';
```

### 9.2 使用 MutationObserver 调试 Live Region

```javascript
const region = document.querySelector('#CartStatus');

const observer = new MutationObserver(() => {
  console.log('Live Region updated:', {
    message: region.textContent,
    role: region.getAttribute('role'),
    live: region.getAttribute('aria-live'),
    busy: region.getAttribute('aria-busy'),
    connected: region.isConnected
  });
});

observer.observe(region, {
  childList: true,
  subtree: true,
  characterData: true,
  attributes: true,
  attributeFilter: [
    'aria-live',
    'aria-busy',
    'aria-hidden',
    'role'
  ]
});
```

结束测试时：

```javascript
observer.disconnect();
```

这个工具能够确认 DOM 是否发生了预期变化，但不能确认屏幕阅读器是否实际完成播报。如果整个节点被替换，还需要检查新的节点并重新建立观察。

### 9.3 Cart Drawer 中一个特殊的通知问题

```html
<main inert>
  <p role="status" id="PageStatus"></p>
</main>

<dialog open>
  <p role="status" id="DrawerStatus"></p>
</dialog>
```

假设此时 Drawer 已真正进入模态状态，通知应该优先由当前活动 Drawer 内部的 `DrawerStatus` 承担。

否则背景页面中的通知节点可能已经无法被辅助技术正常访问。

这里的 `open` 只是用于示意当前显示状态，真实的原生模态弹窗应通过 `showModal()` 打开。

### 9.4 Live Region 重复播报怎么办？

例如切换商品尺寸后同时出现：

```text
Price: $39.99
In stock
Price: $39.99, in stock
```

这通常是因为价格区域、库存区域和统一 Announcer 分别进行了通知。

可以将通知职责集中：

```javascript
function announceVariantChange(variant) {
  status.textContent = [
    variant.formattedPrice,
    variant.available ? 'Available to purchase.' : 'Sold out.'
  ].join(' ');
}
```

这里的 `formattedPrice` 是业务层提供的格式化价格，并非 Shopify Variant 原生字段。

其他价格和库存区域继续正常显示，只是不再重复承担 Live Region 职责。

## 10. 200% Zoom 与 400% Reflow 测试

前面第 8 课学习过响应式布局和文字缩放。现在我们来实际验证它们。

这里需要区分两项 WCAG AA 准则。

| 准则 | 核心要求 |
|---|---|
| 1.4.4 Resize Text | 文字放大至 200% 时，不丢失内容和功能 |
| 1.4.10 Reflow | 普通纵向滚动内容在等效 320 CSS px 宽度下，不需要双向滚动 |

### 10.2 实际测试步骤

document.documentElement.clientWidth;

### 10.3 快速定位横向溢出元素

```javascript
const viewportWidth =
  document.documentElement.clientWidth;

const overflowElements = [
  ...document.querySelectorAll('body *')
].filter(element => {
  const rect = element.getBoundingClientRect();

  return rect.width > 0 &&
    (
      rect.right > viewportWidth + 1 ||
      rect.left < -1
    );
});

console.log(overflowElements);
```

该脚本只能找出候选元素。轮播轨道、视觉隐藏文字和可独立滚动的区域也可能出现在结果中，需要人工判断，不能全部视为错误。

常见修复方式：

```css
.product-info {
  min-width: 0;
  overflow-wrap: anywhere;
}

.product-image {
  max-width: 100%;
  height: auto;
}

.product-actions {
  display: flex;
  flex-wrap: wrap;
}

.product-actions button {
  max-width: 100%;
  white-space: normal;
}
```

不建议为了消除横向滚动条，直接给整个页面添加：

```css
body {
  overflow-x: hidden;
}
```

这可能只是把原本溢出的内容裁切掉，并没有真正解决无障碍问题。

## 11. Text Spacing 文字间距测试

WCAG 1.4.12 Text Spacing（AA）是很多前端开发人员容易遗漏的一项准则。

网站不需要默认采用这些文字间距，但当用户通过样式覆盖进行调整时，不应该造成内容或功能丢失。<Cite ref="turn266530search26"/>

需要测试的参数为：

| 属性 | 测试值 |
|---|---|
| line-height | 至少 1.5 倍字号 |
| 段落之后的间距 | 至少 2 倍字号 |
| letter-spacing | 至少 0.12 倍字号 |
| word-spacing | 至少 0.16 倍字号 |

对于不使用某些文字间距属性的语言和书写系统，存在对应例外。

### 11.3 Shopify 中容易出现问题的位置

| 组件 | 常见原因 |
|---|---|
| Announcement Bar | 固定高度 |
| Add to cart 按钮 | 固定高度、禁止换行 |
| Product Card | 商品名称强制裁切 |
| Inventory Badge | 固定宽高 |
| Cart Drawer | Footer 高度写死 |
| 表单错误提示 | 容器高度不足 |
| Accordion | max-height 限制 |

例如：

```css
/* 不够灵活 */
.add-to-cart {
  height: 44px;
  white-space: nowrap;
  overflow: hidden;
}
```

```css
.add-to-cart {
  min-height: 44px;
  height: auto;
  padding: 12px 16px;
  white-space: normal;
  overflow-wrap: anywhere;
}
```

使用 min-height 而不是固定 height，是很多组件保持文字可访问性的简单办法。

## 12. Forced Colors 高对比度模式

部分低视力用户会通过操作系统的高对比度主题改变网站配色。

这种情况下，浏览器可能使用用户选择的系统颜色替换网站原本的颜色。

特别值得注意的是，`box-shadow` 在 Forced Colors 模式下会被强制设置为 none。<Cite ref="turn266530search1"/>

### 12.1 为什么按钮边框可能消失？

### 12.2 如何进行测试？

在 Chrome DevTools 中打开 Rendering 面板，找到 CSS Media Feature 模拟设置，将 `forced-colors` 设置为 `active`。

也可以在 Windows 中通过：

设置 → 辅助功能 → 对比度主题

开启真实的系统高对比度模式。

后者更适合最终验证。

### 12.3 CSS 修复方案

```css
@media (forced-colors: active) {
  .button {
    border: 1px solid ButtonText;
  }

  .button:focus-visible {
    outline: 2px solid Highlight;
    outline-offset: 3px;
  }

  .variant-input:checked + label {
    border: 2px solid Highlight;
  }

  .icon {
    fill: currentColor;
  }
}
```

常用系统颜色：

| 系统颜色 | 用途 |
|---|---|
| Canvas | 页面背景 |
| CanvasText | 普通文字 |
| ButtonFace | 按钮背景 |
| ButtonText | 按钮文字 |
| Highlight | 高亮状态 |
| HighlightText | 高亮区域文字 |
| GrayText | 禁用状态等 |

### 12.4 Shopify Color Swatch 的特殊处理

商品颜色具有真实业务含义。如果系统颜色覆盖导致所有 Swatch 都变成黑色，用户可能无法通过颜色区分商品。

可以针对单纯的颜色展示区域使用：

```css
@media (forced-colors: active) {
  .swatch-color {
    forced-color-adjust: none;
  }
}
```

但仅应对确实需要保留真实颜色的区域谨慎使用，并保留颜色名称、选中边框和焦点提示。

不要对整个网站设置 `forced-color-adjust: none`，否则可能破坏用户选择高对比度模式的目的。

## 13. Reduced Motion 减少运动测试

除了视觉布局，还需要验证动画偏好。

在 Chrome DevTools 的 Rendering 面板中，可以模拟：

```css
prefers-reduced-motion: reduce
```

推荐重点检查 Shopify 首页轮播、促销公告滚动、商品图片切换、Cart Drawer 滑动动画以及 Quick Add Modal。

### 一个容易被忽略的 JavaScript Bug

假设 Drawer 的焦点管理依赖 CSS 动画结束事件：

```javascript
drawer.addEventListener('transitionend', () => {
  trapFocus(drawer);
}, { once: true });
```

但在减少运动模式下：

```css
@media (prefers-reduced-motion: reduce) {
  .drawer {
    transition: none;
  }
}
```

此时 transitionend 可能根本不会触发，导致 Focus Trap 没有建立。

这是一个视觉优化影响业务生命周期的典型例子。

更合理的架构是：

```text
打开 Drawer
    ↓
立即建立模态隔离和焦点管理
    ↓
根据用户偏好播放可选动画
```

而不是将核心无障碍能力依赖在装饰性动画上。

原生 `dialog.showModal()` 可以承担很大一部分模态基础能力。

减少运动偏好本身并不是 WCAG AA 中针对所有动画的一律禁止要求，但它是很值得纳入测试的工程实践。

## 15. 人工发现问题后的完整修复案例

假设我们在测试 Shopify Cart Drawer 时发现以下问题：

用户通过键盘聚焦 Linen shirt 的 Remove 按钮，按下 Enter 删除该商品，随后 NVDA 不再播报当前购物车操作位置。

### 15.1 问题复现

<box border radius="lg" padding={3} gap={2}>
  <caption>删除之前</caption>
  {#each ["Cotton T-shirt","Linen shirt","Classic jacket"] as n,i}
    <row border radius="sm" padding={2} align="center">
      <text size="sm">{n}</text>
      <spacer/>
      <box border={{size:i===1?2:1,color:i===1?"#3978BC":"#88888850"}} radius="sm" padding={2}><icon name="trash-2" size="sm"/></box>
    </row>
  {/each}
  <box align="center"><icon name="arrow-down"/><caption>删除 Linen shirt，重新渲染购物车</caption></box>
  {#each ["Cotton T-shirt","Classic jacket"] as n}
    <row border radius="sm" padding={2} align="center"><text size="sm">{n}</text><spacer/><icon name="trash-2" size="sm"/></row>
  {/each}
  <row align="center"><icon name="alert-circle" color="danger"/><text size="sm">原焦点节点已经不存在，焦点可能丢失。</text></row>
</box>

### 15.2 定位根因

使用之前的 Console 焦点调试工具，检查：

```javascript
document.activeElement;
```

发现焦点不再位于合理的购物车操作控件上。

进一步检查代码：

```javascript
const response = await changeCartLine(key, 0);

cartItems.innerHTML = responseHTML;
```

根本原因并不是缺少 ARIA 属性，而是原焦点所在 DOM 节点被删除，渲染逻辑没有处理焦点恢复。

### 15.3 修复方案

在 DOM 更新前记录焦点所在购物车行及操作类型，更新完成后优先寻找下一条合理的购物车操作控件。

```javascript
const snapshot = captureCartFocus(cartDrawer);

renderCartItems(response);

if (cartDrawer.open) {
  restoreCartFocus(cartDrawer, snapshot);
}

cartStatus.textContent =
  'Linen shirt removed from your cart.';
```

这里复用了第 23 课的购物车焦点保存与恢复方法。

需要确保：

- 用户仍处于打开的购物车中。
- 请求期间没有主动移动到其他操作区域。
- 新焦点目标仍然存在且可以访问。
- 删除最后一项时存在 Empty Cart 的备用焦点。

### 15.4 修复后的回归测试

| 测试环境 | 验证内容 |
|---|---|
| Keyboard Only | 删除后焦点移动至合理位置 |
| NVDA + Chrome | 感知删除结果及当前操作位置 |
| VoiceOver + Safari | 可以继续浏览剩余购物车 |
| axe-core | 没有引入新的自动检测错误 |
| Empty Cart | 删除最后一项后仍有操作入口 |
| 慢网络 | 不抢夺用户已经转移的焦点 |

这套流程才算真正完成了一次无障碍问题修复。

## 17. 自动检测与人工检测的责任划分

至此，我们可以建立一套完整的无障碍测试职责体系。

| 检测内容 | 推荐手段 |
|---|---|
| ARIA 属性是否合法 | axe-core |
| 按钮是否具有名称 | axe-core |
| 名称是否准确表达业务 | 人工检查 |
| 浏览器计算后的语义 | Chrome DevTools |
| DOM 焦点顺序 | Keyboard + Playwright |
| 屏幕阅读器阅读顺序 | NVDA / VoiceOver |
| Live Region DOM 更新 | Playwright / MutationObserver |
| Live Region 真实播报 | 屏幕阅读器 |
| 文字对比度 | axe / WAVE + 人工判断 |
| Zoom / Reflow | 浏览器缩放测试 |
| Text Spacing | CSS 覆盖测试 |
| Forced Colors | 系统及浏览器模拟 |
| 完整购物流程 | E2E + 人工辅助技术测试 |

值得强调的是，即使我们作为开发者熟练使用屏幕阅读器，也不能完全代替真实残障用户的使用体验。条件允许时，还应该邀请具有辅助技术使用经验的用户参与可用性测试。
