## 3. Principle 1：Perceivable（可感知）

可感知的核心要求是：网站提供的信息不能只依赖某一种感官获取。

例如，不能要求用户必须能够看见图片、区分颜色或者听见声音，才能理解网站内容。

这个原则包含四个指南。

| 编号 | 指南 | 主要内容 |
|---|---|---|
| 1.1 | Text Alternatives | 文本替代 |
| 1.2 | Time-based Media | 音视频等时基媒体 |
| 1.3 | Adaptable | 内容结构与适应性 |
| 1.4 | Distinguishable | 信息可区分性 |

### 3.1 非文本内容：1.1.1（A）

Non-text Content，要求有意义的非文本内容提供适当的文本替代信息。

例如商品图片：

```html
<!-- 不推荐 -->
<img src="product-001.jpg">

<!-- 推荐 -->
<img
  src="product-001.jpg"
  alt="Black cotton T-shirt with crew neck"
>
```

对于装饰性图片，则可以使用空 alt：

```html
<img src="decorative-pattern.png" alt="">
```

这里有一个很重要的原则：alt 的内容应当根据图片在当前页面中的用途决定，而不是机械地描述图片的所有细节。

### 3.2 信息与关系：1.3.1（A）

Info and Relationships，要求通过视觉样式传递的信息、结构和关系，也能够被程序识别，或者以文字形式提供。

例如：

```html
<div class="title">Product details</div>

<div class="list">
  <div>100% cotton</div>
  <div>Machine washable</div>
  <div>Regular fit</div>
</div>
```

即使 CSS 将它们渲染成标题和列表，辅助技术也不一定能够识别这种结构。

正确的方式：

```html
<h2>Product details</h2>

<ul>
  <li>100% cotton</li>
  <li>Machine washable</li>
  <li>Regular fit</li>
</ul>
```

同样的要求还适用于表单标签、表格表头、单选按钮组等。

### 3.3 颜色使用：1.4.1（A）

Use of Color，要求不能仅仅通过颜色传递有意义的信息。

例如 Shopify 商品变体选择器：


### 3.4 最低颜色对比度：1.4.3（AA）

Contrast (Minimum)。

| 文本类型 | AA 要求 | AAA 要求 |
|---|---:|---:|
| 普通文字 | 4.5:1 | 7:1 |
| 大号文字 | 3:1 | 4.5:1 |

WCAG 所说的大号文字通常指至少 18pt（24 CSS px），或至少 14pt（约 18.67 CSS px）的粗体文字。部分特殊内容存在例外，例如品牌 Logo 和纯装饰文字。

颜色对比度不是根据肉眼判断的，而是根据前景色和背景色的相对亮度计算：

\[
\text{Contrast Ratio}=\frac{L_1+0.05}{L_2+0.05}
\]

其中 \(L_1\) 是较亮颜色的相对亮度，\(L_2\) 是较暗颜色的相对亮度。

{@body const ratio=(Math.max(luminance(fgSafe),luminance(bgSafe))+.05)/(Math.min(luminance(fgSafe),luminance(bgSafe))+.05)}

在实际项目中，最容易不满足该准则的通常不是主要标题，而是辅助性文字：

商品原价、配送说明、输入框 placeholder、商品卡片描述、面包屑导航、浅色链接以及表单提示。

### 3.5 非文本对比度：1.4.11（AA）

Non-text Contrast。

文字达标并不代表整个 UI 就达标。

用于识别控件、控件状态以及理解图形信息的必要视觉部分，通常需要与相邻颜色达到至少 3:1 的对比度。

### 3.6 文字缩放与页面重排

这是两个容易混淆的准则。

| 准则 | 等级 | 核心要求 |
|---|---|---|
| 1.4.4 Resize Text | AA | 文字放大至 200% 时不丢失内容或功能 |
| 1.4.10 Reflow | AA | 在规定的窄视口下，不需要双向滚动即可使用内容，规定的例外除外 |
| 1.4.12 Text Spacing | AA | 用户调整规定的文字间距后不丢失内容或功能 |

例如以下 CSS：

```css
.product-title {
  font-size: 18px;
  height: 24px;
  overflow: hidden;
}
```

当用户放大字体后，商品标题可能被裁切。

更合理的写法：

```css
.product-title {
  font-size: 1.125rem;
  line-height: 1.5;
  min-height: 24px;
  overflow-wrap: anywhere;
}
```

使用 rem 并不意味着自动满足 WCAG，最终仍然需要测试页面在缩放、换行和不同视口下的实际表现。

对于常规纵向阅读的网站，Reflow 测试通常会检查 320 CSS px 宽度下的表现，这相当于在初始宽度为 1280 CSS px 的视口中放大至 400% 的效果。

## 4. Principle 2：Operable（可操作）

可操作的核心要求是：用户不应因为无法使用某种输入设备，而无法使用网站提供的功能。

这也是 JavaScript 交互组件开发中涉及最多的原则。

| 编号 | 指南 | 主要内容 |
|---|---|---|
| 2.1 | Keyboard Accessible | 键盘可访问 |
| 2.2 | Enough Time | 提供充足的操作时间 |
| 2.3 | Seizures and Physical Reactions | 避免诱发癫痫及身体不适 |
| 2.4 | Navigable | 页面导航与焦点 |
| 2.5 | Input Modalities | 多种输入方式 |

### 4.1 键盘操作：2.1.1（A）

Keyboard。

网站功能应当可以通过键盘接口完成，除非该功能本质上依赖用户运动轨迹，而不仅仅依赖起点和终点。

例如：

```html
<!-- 错误示例 -->
<div class="button" onclick="openCart()">
  Open cart
</div>
```

```html
<!-- 正确示例 -->
<button type="button" onclick="openCart()">
  Open cart
</button>
```

下面这些电商组件都需要特别关注键盘操作。

| 组件 | 应支持的典型操作 |
|---|---|
| 普通按钮 | Enter、Space |
| 链接 | Enter |
| Radio Group | Tab、方向键、Space |
| Modal | Tab、Shift + Tab，通常支持 Esc 关闭 |
| Tabs | 方向键切换焦点，按设计激活 |
| Accordion | Enter、Space |
| Carousel | 键盘可操作的上一张、下一张按钮 |
| Combobox | 根据组件模式支持方向键、Enter、Esc |

需要区分：WCAG 规定的是无障碍结果，而 WAI-ARIA APG 提供了这些组件的推荐键盘交互模式。

并不是 WCAG 直接规定了每个组件必须使用表格中的所有按键。

### 4.2 无键盘陷阱：2.1.2（A）

No Keyboard Trap。

如果用户能够通过键盘进入某个组件，也必须能够通过键盘离开该组件。

例如用户打开购物车弹窗后，焦点进入了购物车内部。

这里有两个概念需要区分：

- **Focus Trap**：有意将焦点限制在模态弹窗内部，并提供可操作的关闭方式，是合理的设计。
- **Keyboard Trap**：用户进入组件后无法通过键盘退出，是无障碍问题。

我们将在第 11 课和第 15 课详细学习。

### 4.3 跳过重复内容：2.4.1（A）

Bypass Blocks。

假设每个商品详情页顶部都有几十个导航链接。键盘用户每次打开新页面，都必须重复经过这些链接才能进入正文，体验非常差。

因此，可以在页面顶部提供 Skip Link。

```html
<body>
  <a class="skip-link" href="#main-content">
    Skip to main content
  </a>

  <header>
    <!-- Header navigation -->
  </header>

  <main id="main-content" tabindex="-1">
    <!-- Main content -->
  </main>
</body>
```

### 4.4 焦点顺序：2.4.3（A）

Focus Order。

用户通过键盘访问交互元素时，如果顺序会影响理解或操作，那么焦点移动顺序必须保持合理。

例如下面的页面：

<grid columns={2} gap={3}>
  {#each [false,true] as good}
    <grid-item>
      <box border radius="lg" padding={3} gap={2}>
        <text color={good?"success":"danger"} weight="medium">{good?"合理顺序":"混乱顺序"}</text>
        <svg viewBox="0 0 145 160" width="100%">
          {#each ["Email","Password","Remember me","Login"] as t,i}
            <rect x="27" y={7+i*39} width="113" height="28" rx="4" fill="#888888" fillOpacity=".07" stroke="currentColor" strokeOpacity=".25"/>
            <text x="83" y={24+i*39} fontSize="10" textAnchor="middle" fill="currentColor">{t}</text>
            <circle cx="11" cy={21+i*39} r="9" fill={good?"#39866B":"#B65E5E"}/>
            <text x="11" y={25+i*39} fontSize="10" fontWeight="bold" textAnchor="middle" fill="white">{good?i+1:[3,1,4,2][i]}</text>
          {/each}
        </svg>
      </box>
    </grid-item>
  {/each}
</grid>

比较常见的原因是：

- 随意使用正数 `tabindex`。
- CSS Flex/Grid 改变了视觉排列，但没有相应调整 DOM 顺序。
- AJAX 更新之后焦点丢失或跳转到不合理的位置。

CSS 的视觉排列顺序通常不会自动改变默认的 Tab 顺序，因此开发时必须特别注意 DOM 结构。

### 4.5 焦点可见：2.4.7（AA）

Focus Visible。

很多前端项目的全局 CSS 都存在类似代码：

```css
* {
  outline: none;
}
```

如果没有提供其他有效的焦点指示样式，这就可能造成无障碍问题。

更合理的写法：

```css
:focus-visible {
  outline: 2px solid #005fcc;
  outline-offset: 4px;
}
```

    {#each ["View product","Add to cart","Continue shopping"] as t,i}

        </box>
      </box>
    {/each}
  </box>

  <text size="sm" color={focusStyle==="none"?"danger":"success"}>{focusStyle==="none"?"用户无法通过视觉判断当前焦点位置。":"用户可以通过明显的视觉变化识别当前焦点。"}</text>

注意，WCAG AA 的焦点可见要求并没有统一规定必须使用 2px 蓝色 outline。上面的代码只是常见且有效的实现方式，具体样式仍然需要结合背景和组件状态验证。

### 4.6 焦点不被遮挡：2.4.11（AA）

Focus Not Obscured (Minimum)。

这是 WCAG 2.2 新增的准则。

当交互组件获得键盘焦点时，不能被开发者创建的其他内容完全遮挡。

这个问题在电商网站中特别常见，因为很多商品页面具有：

- Sticky Header
- Sticky Add to Cart
- Cookie Banner
- 在线客服悬浮窗
- 固定底部促销栏

<grid columns={2} gap={3}>
  {#each [false,true] as good}

对于此类场景，可以考虑：

```css

  scroll-padding-top: 80px;
  scroll-padding-bottom: 100px;

```

实际数值应该根据固定 Header 和底部栏的高度设置，并结合真实的键盘导航测试。

另外要区分两个级别：

| 准则 | 要求 |
|---|---|
| 2.4.11 AA | 获得焦点的组件不被完全遮挡 |
| 2.4.12 AAA | 获得焦点的组件任何部分均不被遮挡 |

### 4.7 点击目标大小：2.5.8（AA）

## 5. Principle 3：Understandable（可理解）

可理解的核心要求是：用户不仅能够获取信息和操作功能，还应该能够理解信息的含义、操作的方式及操作产生的结果。

| 编号 | 指南 | 主要内容 |
|---|---|---|
| 3.1 | Readable | 内容可阅读 |
| 3.2 | Predictable | 交互可预测 |
| 3.3 | Input Assistance | 输入辅助与错误处理 |

### 5.1 页面语言：3.1.1（A）

Language of Page。

网页的主要语言应该能够被程序识别。

```html
<html lang="en">
```

屏幕阅读器可以根据语言信息选择合适的语音发音规则。

对于 Shopify 多语言网站，可以使用 Liquid 动态输出当前页面语言：

```liquid
<html lang="{{ request.locale.iso_code }}">
```

另外，3.1.2（AA）要求能够识别内容中符合条件的局部语言变化。

例如：

```html
<p>
  Our French collection is called
  <span lang="fr">Bonjour Paris</span>.
</p>
```

但并不是每个外语单词、专有名词或者技术术语都需要设置 lang。

### 5.2 输入时的可预测性：3.2.2（A）

On Input。

改变表单控件的设置时，不应该在没有提前告知用户的情况下自动引发上下文变化。

例如：

```javascript
languageSelect.addEventListener('change', () => {
  window.location.href = languageSelect.value;
});
```

如果用户使用键盘浏览语言选择框中的选项，可能还没有完成选择，页面就已经发生导航。

一种更清晰的实现是：

```html
<label for="language">Language</label>

<select id="language" name="language">
  <option value="en">English</option>
  <option value="fr">Français</option>
</select>

<button type="submit">Apply language</button>
```

当然，这并不意味着所有 `change` 事件都不能更新页面。

例如切换 Shopify 商品 Variant 后更新价格、库存、图片，或者 Collection 筛选后更新商品列表，通常并不必然构成违反该准则的上下文变化。

关键在于变化是否会使用户失去原有操作环境，以及是否具有合理的可预测性。

### 5.3 标签与说明：3.3.2（A）

Labels or Instructions。

需要用户输入信息时，应提供适当的标签或说明。

```html
<!-- 不推荐 -->
<input type="email" placeholder="Email address">
```

```html
<!-- 推荐 -->
<label for="email">Email address (required)</label>

<input
  type="email"
  id="email"
  name="email"
  autocomplete="email"
  required
>
```

Placeholder 不能完全替代持久可见的 label，因为用户输入内容之后，placeholder 就会消失。

### 5.4 错误识别与错误建议

这两个准则经常同时出现在 ADA 审计报告中。

| 准则 | 等级 | 要求 |
|---|---|---|
| 3.3.1 Error Identification | A | 识别错误字段，并通过文字描述错误 |
| 3.3.3 Error Suggestion | AA | 在已知可行修复方法且没有规定例外时，提供修复建议 |

例如电商网站注册表单：

<grid columns={2} gap={3}>
  <grid-item>
    <box border radius="lg" padding={3} gap={2}>
      <text color="danger" weight="medium">错误示例</text>
      <caption>Email address</caption>
      <box border={{size:2,color:"#C65353"}} radius="sm" padding={2}>
        <text size="sm">example.com</text>
      </box>
      <box background="surface-tertiary" radius="sm" padding={2} align="center">Submit</box>
      <caption>仅显示红色边框，用户不知道错误原因。</caption>
    </box>
  </grid-item>
  <grid-item>
    <box border radius="lg" padding={3} gap={2}>
      <text color="success" weight="medium">正确示例</text>
      <caption>Email address</caption>
      <box border={{size:2,color:"#C65353"}} radius="sm" padding={2}>
        <text size="sm">example.com</text>
      </box>
      <row align="start" gap={1}>
        <icon name="alert-circle" color="danger" size="sm"/>
        <box flex={1}><text color="danger" size="xs">Enter a valid email address, such as name@example.com.</text></box>
      </row>
      <box background="surface-tertiary" radius="sm" padding={2} align="center">Submit</box>
    </box>
  </grid-item>
</grid>

对应的 HTML 可以这样实现：

```html
<label for="email">Email address</label>

<input
  type="email"
  id="email"
  aria-invalid="true"
  aria-describedby="email-error"
>

<p id="email-error">
  Enter a valid email address,
  such as name@example.com.
</p>
```

其中：

`aria-invalid` 用于告知辅助技术当前输入值无效。

`aria-describedby` 用于建立输入框和错误说明之间的关系。

如果错误信息是动态插入的，还需要根据实际交互考虑错误播报或焦点管理。

### 5.5 防止重要操作错误：3.3.4（AA）

Error Prevention (Legal, Financial, Data)。

对于涉及法律承诺、金融交易、重要数据修改等操作的页面，需要提供规范要求的错误预防机制之一，例如允许撤销、检查输入错误，或者提交前确认和更正信息。

这在电商网站的 Checkout 中特别重要。

提供订单确认、修改商品数量、检查收货地址等功能，不仅是良好的业务体验，也涉及无障碍错误预防。

### 5.6 避免重复输入：3.3.7（A）

Redundant Entry。

这是 WCAG 2.2 新增的准则。

在同一个操作流程中，如果用户之前已经输入或提供过某项信息，而后续步骤再次需要该信息，通常应当自动填充或者允许用户选择已有信息。

例如 Checkout 中的配送地址与账单地址：

{@body const [sameAddress,setSameAddress]=DIL.useState(true)}
<card gap={3}>
  **Shipping address**
  <box background="surface-tertiary" radius="md" padding={3}>
    <text size="sm">Alex Smith</text>
    <text size="sm">123 Example Street</text>
    <text size="sm">Los Angeles, CA 90001</text>
  </box>
  <divider/>
  **Billing address**
  <checkbox checked={sameAddress} onChange={setSameAddress}>Same as shipping address</checkbox>
  {#if sameAddress}
    <row align="center">
      <icon name="check-circle" color="success"/>
      <caption>使用已经提供的配送地址</caption>
    </row>
  {:else}
    <label>Full name</label>
    <input placeholder="Full name"/>
    <label>Street address</label>
    <input placeholder="Street address"/>
    <label>City</label>
    <input placeholder="City"/>
  {/if}
</card>

安全需要、信息已经失效以及重复输入本身不可替代的情况，可能属于例外。

## 6. Principle 4：Robust（健壮性）

健壮性的核心要求是：网页内容能够被浏览器、辅助技术等用户代理可靠地解释。

这一原则只有一个指南。

| 编号 | 指南 | 主要内容 |
|---|---|---|
| 4.1 | Compatible | 兼容性 |

但它包含两个对现代前端开发特别重要的成功准则。

### 6.1 名称、角色、值：4.1.2（A）

Name, Role, Value。

这条准则在复杂 JavaScript 组件的 ADA 审计报告中非常常见。

其核心要求包括：UI 组件的名称和角色能够被程序识别，用户可设置的状态、属性和值能够通过程序设置，相关变化能够提供给用户代理及辅助技术。

这恰好对应我们上一课学习的 Accessibility Tree。

例如一个自定义收藏按钮：

```html
<div class="favorite active" onclick="toggleFavorite()">
  <svg>
    <!-- Heart icon -->
  </svg>
</div>
```

虽然视觉用户能够看到收藏图标变成红色，但是辅助技术可能无法知道它是什么、叫什么、是否已经收藏。

正确的实现：

```html
<button
  type="button"
  aria-label="Favorite"
  aria-pressed="false"
>
  <svg aria-hidden="true">
    <!-- Heart icon -->
  </svg>
</button>
```

JavaScript 在切换收藏状态时同步更新 `aria-pressed`。

{@body const [isFav,setIsFav]=DIL.useState(false)}
<card gap={3}>
  <box align="center" padding={3}>
    <button size="xl" variant="outline" color="secondary" onClick={()=>setIsFav(!isFav)}>
      <icon name="heart" size="3xl" color={isFav?"#C65368":"secondary"}/>
      Favorite
    </button>
  </box>
  <box border radius="md" padding={3} gap={2}>
    <caption>Accessibility Node</caption>
    <row><text size="sm">Name</text><spacer/>Favorite</row>
    <row><text size="sm">Role</text><spacer/>button</row>
    <row><text size="sm">Pressed</text><spacer/><text color={isFav?"success":"secondary"}>{String(isFav)}</text></row>
  </box>
  <row align="center">
    <icon name="volume-2" size="xl"/>
    <box flex={1}>
      <caption>模拟屏幕阅读器播报</caption>
      **Favorite, toggle button, {isFav?"pressed":"not pressed"}.**
    </box>
  </row>
</card>

常见的 4.1.2 问题包括：

| 组件 | 典型问题 |
|---|---|
| Icon Button | 缺少可访问名称 |
| Accordion | 缺少展开或折叠状态 |
| Tabs | 缺少选中状态 |
| Custom Select | 缺少角色、名称或值 |
| Slider | 缺少当前值及范围信息 |
| Variant Picker | 无法获取选中状态 |
| Dialog | 缺少对话框角色或名称 |

后续 ARIA 和复杂组件开发阶段，我们会频繁涉及这条准则。

### 6.2 状态消息：4.1.3（AA）

Status Messages。

用户执行操作后，如果网站在不改变上下文的情况下展示状态消息，那么这些消息应当可以通过适当的角色或属性被辅助技术获取，而无需主动接收焦点。

例如 Shopify AJAX 加购：

```html
<div
  id="cart-status"
  role="status"
  class="visually-hidden"
></div>
```

```javascript
// 实际加购请求成功之后执行
cartStatus.textContent =
  'Cotton T-shirt added to your cart.';
```

再比如 Collection AJAX 筛选。

{@body const [filter,setFilter]=DIL.useState("all")}
{@body const results={all:128,black:36,white:42,blue:50}}
<card gap={3}>
  **Collection 筛选演示**
  <label>Color</label>
  <radio-group direction="row" value={filter} onChange={setFilter}>
    <radio value="all">All</radio>
    <radio value="black">Black</radio>

  <divider/>

          <path d="M31 15 L11 28 L22 49 L31 42 V87 H59 V42 L68 49 L79 28 L59 15 L53 22 H37 Z" fill={filter==="all"?["#3A3A3A","#F5F4F1","#6A829C"][i]:{black:"#3A3A3A",white:"#F5F4F1",blue:"#6A829C"}[filter]} stroke="#888888" strokeOpacity=".4"/>

筛选完成后，可以让用户在继续操作筛选控件的同时，获知当前筛选结果的商品数量。

没有必要仅仅为了通知商品数量变化，就强行将焦点移动到商品列表。

这也是 Live Region 与 Focus Management 之间的一个重要区别。

## 7. WCAG A、AA、AAA 到底有什么区别？

<box border radius="lg" padding={3} gap={3}>
  <svg viewBox="0 0 340 192" width="100%">
    <rect x="8" y="5" width="324" height="180" rx="9" fill="#39866B" fillOpacity=".07" stroke="#39866B" strokeOpacity=".5"/>
    <text x="20" y="25" fontSize="13" fontWeight="600" fill="currentColor">AAA · 全部 86 条</text>
    <rect x="25" y="39" width="290" height="133" rx="7" fill="#39866B" fillOpacity=".12" stroke="#39866B" strokeOpacity=".6"/>
    <text x="38" y="60" fontSize="13" fontWeight="600" fill="currentColor">AA · 累计 55 条</text>
    <rect x="43" y="75" width="254" height="82" rx="6" fill="#39866B" fillOpacity=".23" stroke="#39866B"/>
    <text x="170" y="108" fontSize="20" fontWeight="600" textAnchor="middle" fill="currentColor">A</text>
    <text x="170" y="131" fontSize="12" textAnchor="middle" fill="currentColor">31 条基础成功准则</text>
  </svg>
  <divider/>
  <row>
    **Level A**
    <spacer/>
    <caption>31 条</caption>
  </row>
  <row>
    **Level AA**
    <spacer/>
    <caption>31 + 24 = 55 条</caption>
  </row>
  <row>
    **Level AAA**
    <spacer/>
    <caption>31 + 24 + 31 = 86 条</caption>
  </row>
  <caption>WCAG 2.2 成功准则数量，按已移除 4.1.1 计算。</caption>
</box>

这里有几个容易误解的地方。

**第一，满足 AA 必须同时满足 A。**

不能只修复 AA 级问题，而忽略 A 级问题。

**第二，WCAG 合规等级不是百分制评分。**

假设一个网站通过了 54 条 A 和 AA 准则，但有一条适用准则没有满足，那么它仍然不能宣称已经完全符合 WCAG 2.2 AA。

**第三，A、AA、AAA 不等于 Bug 的严重程度。**

审计报告中的 Critical、Serious、Moderate、Minor 属于问题影响程度分类，与 WCAG 合规等级是两个不同的体系。

例如：

| 问题 | WCAG 等级 | 可能的严重程度 |
|---|---|---|
| 无法通过键盘完成付款 | A | Critical |
| 商品装饰性图标存在多余语义 | 视实际情况 | Minor |
| 正文颜色对比度不足 | AA | Serious |
| 固定底部栏完全遮挡焦点 | AA | Serious |

实际严重程度需要根据受影响的用户、功能和业务流程确定。

**第四，合规是针对完整页面和完整流程的。**

WCAG 要求完整页面满足相应准则。如果页面属于一个完整的操作流程，那么该流程中的所有页面也必须达到相应等级。<Cite ref="turn234267search2"/>

<box border radius="lg" padding={3} gap={1}>
  {#each [{name:"Homepage",ok:true},{name:"Collection",ok:true},{name:"Product Detail",ok:true},{name:"Cart",ok:true},{name:"Checkout",ok:false}] as item,i}
    <row border radius="md" padding={3} align="center">
      <text weight="medium">{item.name}</text>
      <spacer/>
      <icon name={item.ok?"check-circle":"x-circle"} color={item.ok?"success":"danger"}/>
      <text size="sm" color={item.ok?"success":"danger"}>{item.ok?"假设达标":"未达标"}</text>
    </row>
    {#if i<4}<box align="center"><icon name="arrow-down" color="secondary" size="sm"/></box>{/if}
  {/each}
  <divider/>
  <text color="danger" weight="medium">完整购买流程未达到目标合规等级</text>
</box>

这意味着即使 Shopify Theme 本身做得非常好，如果第三方 App、评论组件、支付流程或其他内容引入了无障碍问题，仍然需要将这些问题纳入整体评估。

## 8. WCAG 2.0、2.1、2.2 有什么区别？

<box border radius="lg" padding={3} gap={3}>
  <list connector="solid" marker="number" gap={3}>
    <list-item>
      **WCAG 2.0**

      <caption>2008 年 12 月 11 日</caption>

      61 条成功准则，建立 POUR、A/AA/AAA 体系以及基础网页无障碍要求。
    </list-item>
    <list-item>
      **WCAG 2.1**

      <caption>2018 年 6 月 5 日</caption>

      原始发布版本共 78 条准则，在 2.0 基础上增加移动设备、低视力、认知障碍及输入方式等方面的要求。
    </list-item>
    <list-item>
      **WCAG 2.2**

      <caption>2023 年 10 月 5 日</caption>

      新增 9 条准则，移除已经过时的 4.1.1 Parsing，共 86 条准则。
    </list-item>
  </list>
</box>

WCAG 2.2 新增的九条准则如下：

| 编号 | 名称 | 等级 |
|---|---|---|
| 2.4.11 | 焦点不被完全遮挡 | AA |
| 2.4.12 | 焦点完全不被遮挡 | AAA |
| 2.4.13 | 焦点外观 | AAA |
| 2.5.7 | 拖拽操作替代方式 | AA |
| 2.5.8 | 最小目标尺寸 | AA |
| 3.2.6 | 一致的帮助入口 | A |
| 3.3.7 | 避免重复输入 | A |
| 3.3.8 | 无障碍身份验证（最低要求） | AA |
| 3.3.9 | 无障碍身份验证（增强要求） | AAA |

W3C 在 2.2 中移除了原有的 4.1.1 Parsing 准则，但这并不意味着开发者可以忽略 HTML 结构错误。例如重复 ID 导致 label 或 ARIA 引用错误，仍然可能违反其他适用准则。<Cite ref="turn234267search1"/>

对于我们这套课程以及新开发的跨境电商网站，建议以 **WCAG 2.2 AA** 作为技术目标，同时核对公司合同、审计要求以及具体市场的法律要求。

美国 ADA Title II 针对州和地方政府网站的技术规则采用 WCAG 2.1 AA，而私人商业网站涉及的 Title III 合规问题不能直接与之等同。达到某个 WCAG 等级也不意味着自动获得法律免责。<Cite refs={["turn234267search27","turn234267search29"]}/>

## 9. 如何阅读一份 ADA Audit Report？

这部分与你实际工作中的 ADA 修复任务关系很大。

假设公司委托第三方进行网站无障碍审计，你收到以下报告。

  <row align="center">
    <icon name="file-text" size="xl"/>

    </box>

  </row>
  <row>
    <caption>Severity</caption>
    <spacer/>
    <badge color="danger">Serious</badge>
  </row>
  <row>
    <caption>WCAG</caption>
    <spacer/>
    <text size="sm">4.1.2 · Level A</text>
  </row>
  <row>
    <caption>Page</caption>
    <spacer/>
    <text size="sm">Product detail page</text>
  </row>
  <row>

  </row>
  <divider/>
  **Observed Behavior**

  <text size="sm">The shopping cart button is announced as an unlabeled button by the screen reader.</text>

  **Expected Behavior**

  <text size="sm">The button should have a meaningful accessible name that identifies its purpose.</text>

  **User Impact**

  <text size="sm">Screen reader users may be unable to determine the purpose of the shopping cart button.</text>

  **Recommendation**

  <text size="sm">Provide a descriptive accessible name using appropriate HTML or ARIA.</text>
</card>

作为前端工程师，收到这份报告后应该怎么处理？

### 第一步：复现问题

找到对应元素：

```html
<button id="cart-icon-bubble">
  <svg>
    <!-- Cart icon -->
  </svg>
</button>
```

使用 NVDA 访问该按钮，可能只听到：

> Button.

再打开 Chrome DevTools 的 Accessibility 面板，检查 Name 是否为空。

### 第二步：理解对应的 WCAG 准则

在报告中找到：

```text
WCAG 4.1.2 — Name, Role, Value
Level A
```

通过 [Understanding 4.1.2](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) 阅读该准则的目的和实现建议。

### 第三步：修复代码

对于纯图标按钮，可以使用 `aria-label`。

```liquid
<button
  type="button"
  id="cart-icon-bubble"
  aria-label="{{ 'templates.cart.cart' | t | escape }}"
>
  <svg aria-hidden="true" focusable="false">
    <!-- Cart icon -->
  </svg>
</button>
```

这里使用 Shopify 翻译机制，而不是将英文名称直接硬编码在模板里。具体翻译 key 需要根据当前 Theme 的 locale 文件确定。

### 第四步：验证修复结果

  <grid-item>
    <box border radius="lg" padding={3} gap={2}>
      <text color="danger" weight="medium">修复前</text>
      <box align="center" padding={3}><icon name="shopping-cart" size="3xl"/></box>
      <divider/>
      <caption>Role</caption>
      button
      <caption>Name</caption>
      <text color="danger">空</text>
      <divider/>
      <caption>模拟播报</caption>
      “Button.”
    </box>
  </grid-item>
  <grid-item>
    <box border radius="lg" padding={3} gap={2}>
      <text color="success" weight="medium">修复后</text>
      <box align="center" padding={3}><icon name="shopping-cart" size="3xl"/></box>
      <divider/>
      <caption>Role</caption>
      button
      <caption>Name</caption>
      <text color="success">Cart</text>
      <divider/>
      <caption>模拟播报</caption>
      “Cart, button.”
    </box>
  </grid-item>
</grid>

两者的视觉表现完全一样，但无障碍表现已经发生变化。

除了检查 Name，还需要验证按钮可以通过键盘激活、打开购物车后焦点正确转移，并且关闭后焦点能够合理恢复。

完整的 ADA 修复工作流应当是：

<box border radius="lg" padding={3} gap={1}>
  {#each ["收到 Audit Report","定位页面、组件和 DOM 元素","使用辅助技术复现问题","查询对应 WCAG 成功准则","分析根本原因","修复 HTML / CSS / JavaScript","进行自动化和人工回归测试","记录修复结果与测试证据"] as step,i}
    <box border radius="md" padding={2} align="center">
      <text weight="medium" size="sm">{step}</text>
    </box>
    {#if i<7}<box align="center"><icon name="arrow-down" size="sm" color="secondary"/></box>{/if}
  {/each}
</box>

不要仅仅根据审计报告的 Recommendation 添加一个 ARIA 属性就结束任务。必须理解它解决了什么问题，以及是否引入了新的问题。

## 11. 如何将 WCAG 融入前端开发流程？

无障碍不应该只是测试团队最后负责的工作，而应该在每个开发阶段落实。

| 阶段 | 无障碍关注点 |
|---|---|
| 产品需求 | 功能是否具有替代操作方式 |
| UI 设计 | 对比度、点击区域、焦点样式、错误提示 |
| HTML 开发 | 语义化、Heading、Label、Landmark |
| CSS 开发 | 缩放、响应式、内容隐藏、视觉状态 |
| JavaScript 开发 | 键盘交互、焦点管理、ARIA 状态 |
| AJAX 开发 | 动态内容变化、状态消息 |
| Code Review | 检查语义、状态与交互是否一致 |
| QA 测试 | axe、Lighthouse、键盘、屏幕阅读器 |
| 上线维护 | 第三方 App、新增内容和组件回归测试 |

例如开发一个 Shopify 商品变体选择器时，不应该等到测试阶段才考虑无障碍，而应该从选择 HTML 标签开始，就确定它的 Role、Name、State、键盘操作方式和视觉状态。

这样修复成本会低得多。
