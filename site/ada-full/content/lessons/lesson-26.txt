这套体系的核心思想叫作 **Shift Left（质量左移）**：尽可能在设计和开发阶段发现问题，而不是等网站上线之后再集中整改。

| 发现问题的阶段 | 典型修复方式 |
|---|---|
| 设计阶段 | 修改设计规范和组件设计 |
| 开发阶段 | 修改当前组件代码 |
| Code Review | 阻止错误代码合并 |
| 自动化测试阶段 | 定位回归问题 |
| 上线后 | 涉及多个页面、组件及重新发布 |
| 用户投诉后 | 除技术整改外，还可能涉及业务和法律风险 |

无障碍不应该是项目上线之前的一项临时任务，而应该成为整个软件开发生命周期的一部分。

| 测试层级 | 工具 | 主要检查内容 |
|---|---|---|
| 静态检查 | Theme Check、ESLint | 源码及编码规范 |
| 组件检测 | Playwright、axe-core | 名称、角色、状态、焦点 |
| E2E 检测 | Playwright | 搜索、筛选、加购、结算 |
| 人工检测 | NVDA、VoiceOver | 真实辅助技术使用体验 |

例如开发一个新的 Cart Drawer：

静态检查负责发现代码问题，组件测试负责验证打开和关闭行为，E2E 测试负责验证加购后的购物车流程，人工测试则负责验证屏幕阅读器用户能否真正使用这个组件。

每一层都有独立的价值，不能相互完全替代。

## 3. 静态代码检测：Theme Check 与 ESLint

### 3.1 Shopify Theme Check

Theme Check 是 Shopify 官方提供的 Liquid 和 JSON 静态检查工具，也集成在官方 Liquid VS Code 扩展中。<Cite ref="turn120024search5"/>

在 Theme 项目根目录执行：

```bash
shopify theme check
```

它主要检查 Liquid 语法、模板引用、性能及 Shopify Theme 开发规范等问题。

不过，Theme Check 并不是完整的无障碍检测工具。

例如：

```liquid
<button>
  {% render 'icon-search' %}
</button>
```

即使这段 Liquid 完全符合语法规则，也不能保证最终生成的 button 具有 Accessible Name。

因为静态检查工具没有完整的运行时 DOM、CSS、无障碍树和用户交互状态。

### 3.2 ESLint 与 jsx-a11y

如果项目使用 React，可以通过 `eslint-plugin-jsx-a11y` 检查 JSX 中的一部分无障碍问题，例如：

| Rule | 检查内容 |
|---|---|
| `alt-text` | 图片替代文本 |
| `anchor-is-valid` | 链接是否合理 |
| `label-has-associated-control` | Label 与控件关联 |
| `click-events-have-key-events` | 点击交互的键盘支持 |
| `no-static-element-interactions` | 非交互元素上的交互行为 |
| `aria-props` | ARIA 属性是否合法 |

但是，传统 Shopify Theme 使用 Liquid，而不是 JSX，因此不能直接依靠 jsx-a11y 检测 `.liquid` 文件。

对于你的 Shopify Theme 项目，更合理的组合是：

```text
Liquid / JSON  → Theme Check
JavaScript     → ESLint
Rendered HTML  → axe-core
User Behavior  → Playwright
真实辅助技术    → NVDA / VoiceOver
```

### 3.3 团队自定义静态规则

还可以根据项目实际情况补充内部规则，例如禁止正数 tabindex、禁止移除焦点样式后不提供替代样式、要求纯图标按钮具备可访问名称。

但是不要通过简单正则表达式就认定所有匹配代码都是 WCAG 违规。Liquid 条件渲染、HTML 上下文及组件封装都可能影响最终结果。

### 4.3 Playwright 配置

创建 `playwright.config.ts`：

```typescript
import { defineConfig, devices } from '@playwright/test';

const baseURL = process.env.STOREFRONT_URL;

if (!baseURL) {
  throw new Error('STOREFRONT_URL is required');
}

export default defineConfig({
  testDir: './tests',

  fullyParallel: false,

  forbidOnly: !!process.env.CI,

  retries: process.env.CI ? 1 : 0,

  workers: process.env.CI ? 1 : undefined,

  reporter: [
    ['list'],
    ['html', { open: 'never' }],
    ['json', {
      outputFile: 'test-results/results.json'
    }]
  ],

  use: {
    baseURL,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  },

  projects: [
    {
      name: 'desktop-chromium',
      use: {
        ...devices['Desktop Chrome']
      }
    },
    {
      name: 'mobile-webkit',
      use: {
        ...devices['iPhone 13']
      }
    }
  ]
});
```

这套配置同时检测桌面 Chromium 和模拟移动端 WebKit。

需要注意，Playwright 的 iPhone 设备配置只模拟部分移动设备及浏览器特征，不能代替真实 iPhone 的 Safari 和 VoiceOver 测试。

`STOREFRONT_URL` 应指向实际运行的测试店铺或预览环境，而不是本地存放 Liquid 源码的静态文件服务器。Shopify 的 Liquid 必须经过平台渲染。

## 5. 封装统一的 axe-core 检测工具

每一个测试文件都重复编写 AxeBuilder 配置，维护起来会非常麻烦。

因此可以统一封装。

创建 `tests/helpers/accessibility.ts`：

```typescript
import AxeBuilder from '@axe-core/playwright';

import {
  expect,
  type Page,
  type TestInfo
} from '@playwright/test';

const WCAG_TAGS = [
  'wcag2a',
  'wcag2aa',
  'wcag21a',
  'wcag21aa',
  'wcag22a',
  'wcag22aa'
];

export async function scanAccessibility(
  page: Page,
  testInfo: TestInfo,
  state: string
) {
  const results = await new AxeBuilder({ page })
    .withTags(WCAG_TAGS)
    .analyze();

  // 将原始结果作为测试报告附件
  await testInfo.attach(`axe-${state}.json`, {
    body: JSON.stringify(results, null, 2),
    contentType: 'application/json'
  });

  const violations = results.violations.flatMap(rule =>
    rule.nodes.map(node => ({
      rule: rule.id,
      impact: node.impact ?? rule.impact,
      target: node.target,
      reason: node.failureSummary,
      reference: rule.helpUrl
    }))
  );

  expect(
    violations,
    `Accessibility violations in ${state}`
  ).toEqual([]);

  return results;
}
```

Playwright 官方支持通过 `@axe-core/playwright` 运行检测、按规则标签筛选，以及使用公共 Fixture 统一配置。<Cite ref="turn120024search15"/>

这里封装了四项能力：

- 统一 WCAG 检测范围。
- 保存完整的 axe JSON 报告，包括 Incomplete。
- 提取易于开发者定位的问题。
- 存在自动检测违规时，使测试失败。

这样以后只需要调用：

```typescript
await scanAccessibility(page, testInfo, 'cart-open');
```

就可以执行统一的无障碍检测。

注意：这里的零违规断言只是自动化质量门禁，不代表覆盖了 WCAG 2.2 AA 的全部要求。

## 6. 页面状态自动化测试

上一课已经强调过，一个 URL 不等于一个页面状态。

例如首页默认状态没有任何无障碍问题，不代表打开 Header Mega Menu 后也没有问题。

### 6.1 建立测试覆盖矩阵

| 页面 | 必测状态 |
|---|---|
| Homepage | 默认、轮播切换、促销弹窗 |
| Header | Mega Menu、移动端导航、搜索建议 |
| Collection | 默认、筛选、排序、无结果 |
| Product | 有货、售罄、Variant 切换、图片放大 |
| Cart Drawer | 打开、修改数量、删除、空购物车 |
| Checkout | 地址错误、配送选择、支付确认 |

每种状态都可以独立执行 axe 扫描，同时增加业务及焦点断言。

### 6.2 Homepage 测试

创建 `tests/accessibility/homepage.spec.ts`：

```typescript
import { test, expect } from '@playwright/test';
import { scanAccessibility } from '../helpers/accessibility';

test('homepage accessibility', async ({ page }, testInfo) => {
  await page.goto('/');

  await expect(
    page.locator('#MainContent')
  ).toBeVisible();

  await scanAccessibility(
    page,
    testInfo,
    'homepage-default'
  );
});
```

### 6.3 Cart Drawer 动态状态测试

创建 `tests/accessibility/cart.spec.ts`：

```typescript
import { test, expect } from '@playwright/test';
import { scanAccessibility } from '../helpers/accessibility';

test('cart drawer accessibility', async ({ page }, testInfo) => {
  await page.goto('/products/cotton-tshirt');

  const addButton = page.getByRole('button', {
    name: 'Add to cart',
    exact: true
  });

  await expect(addButton).toBeEnabled();

  await addButton.click();

  const drawer = page.getByRole('dialog', {
    name: 'Your cart'
  });

  await expect(drawer).toBeVisible();

  await expect(
    drawer.getByText('Cotton T-shirt', { exact: true })
  ).toBeVisible();

  await scanAccessibility(
    page,
    testInfo,
    'cart-drawer-open'
  );

  await drawer.getByRole('button', {
    name: 'Close shopping cart'
  }).click();

  await expect(drawer).toBeHidden();

  await scanAccessibility(
    page,
    testInfo,
    'cart-drawer-closed'
  );
});
```

这个测试覆盖打开和关闭两种状态。关闭状态同样值得扫描，因为隐藏 Drawer 中的交互控件可能仍然具有焦点能力。

本例假设使用英文测试店铺，存在固定商品，并且店铺配置为加购后自动打开 Cart Drawer。

## 7. 无障碍行为的自动化断言

axe-core 可以检查语义问题，但是无法充分理解业务行为是否正确。

因此需要使用 Playwright 自身的断言能力。

### 7.1 常用无障碍断言

| Playwright API | 检测内容 |
|---|---|
| `getByRole()` | 按语义角色定位元素 |
| `getByLabel()` | 按表单名称定位 |
| `toHaveAccessibleName()` | 验证可访问名称 |
| `toHaveAccessibleDescription()` | 验证可访问描述 |
| `toBeFocused()` | 验证当前焦点 |
| `toBeChecked()` | 验证选中状态 |
| `toBeDisabled()` | 验证禁用状态 |
| `toHaveAttribute()` | 验证 ARIA 属性 |
| `toMatchAriaSnapshot()` | 验证无障碍语义结构 |

### 7.2 为什么优先使用 getByRole？

传统测试代码：

```typescript
const button = page.locator('.header-search-icon');

await button.click();
```

推荐使用：

```typescript
const button = page.getByRole('button', {
  name: 'Search',
  exact: true
});

await button.click();
```

第二种方式不仅可以找到控件，还间接验证了它具有合理的角色及名称。

假设其他开发人员将 Search 按钮改成：

```html
<div class="header-search-icon">
  <svg></svg>
</div>
```

基于 CSS Selector 的测试可能仍然通过，但基于 Role 的测试将无法找到预期按钮。

这使得无障碍要求自然融入了普通业务测试。

### 7.3 测试 Modal 的完整焦点生命周期

```typescript
test('cart drawer keyboard behavior', async ({ page }, testInfo) => {
  test.skip(
    testInfo.project.name !== 'desktop-chromium',
    'Desktop keyboard interaction test'
  );

  await page.goto('/');

  const trigger = page.getByRole('button', {
    name: /shopping cart/i
  });

  await trigger.focus();
  await page.keyboard.press('Enter');

  const drawer = page.getByRole('dialog', {
    name: 'Your cart'
  });

  await expect(drawer).toBeVisible();

  const closeButton = drawer.getByRole('button', {
    name: 'Close shopping cart'
  });

  // 此测试假设初始焦点规范为关闭按钮
  await expect(closeButton).toBeFocused();

  await page.keyboard.press('Escape');

  await expect(drawer).toBeHidden();

  await expect(trigger).toBeFocused();
});
```

对于 Focus Trap，还应该单独验证 Tab、Shift + Tab 在边界上的行为。

### 7.4 测试 Variant Picker

```typescript
test('variant picker semantics', async ({ page }) => {
  await page.goto('/products/cotton-tshirt');

  const color = page.getByRole('group', {
    name: 'Color',
    exact: true
  });

  const black = color.getByRole('radio', {
    name: 'Black',
    exact: true
  });

  await black.check();

  await expect(black).toBeChecked();
  await expect(black).toHaveAccessibleName('Black');

  await expect(
    page.locator('[data-variant-status]')
  ).toContainText('In stock');
});
```

实际项目应准备固定 Variant 数据，并进一步验证提交的 Variant ID、实际价格以及库存状态。

**无障碍测试与业务测试并不是两套完全独立的体系。** 很多高质量的业务自动化测试，本身就能够承担一部分无障碍回归检测职责。

## 8. Accessibility Snapshot 与 ARIA Snapshot

这是非常值得前端开发工程师掌握的测试能力。

普通 Screenshot Snapshot 关注的是页面视觉表现，而 ARIA Snapshot 关注的是页面提供给辅助技术的语义结构。

Playwright 现在提供 `toMatchAriaSnapshot()` 用于验证 ARIA 快照。新项目可以优先使用这套能力，而不是依赖旧式的 `page.accessibility.snapshot()` API。<Cite ref="turn120024search2"/>

### 8.1 三种快照的区别

<grid columns={2} gap={3}>
  <grid-item>
    <box border radius="md" padding={3} gap={2}>
      **Visual Snapshot**
      <box background="#E5DED3" radius="sm" padding={2}>
        <svg viewBox="0 0 120 105" width="100%">
          <path d="M40 7 L9 26 L25 47 L40 38 V99 H80 V38 L95 47 L111 26 L80 7 L60 17 Z" fill="#555555"/>
        </svg>
      </box>
      <text size="sm" weight="medium">Cotton T-shirt</text>
      **$29.99**
      <box background="#333333" theme="dark" radius="sm" padding={2} align="center"><text color="#FFFFFF" size="sm">Add to cart</text></box>
      <caption>检查布局、颜色、图像等视觉变化。</caption>
    </box>
  </grid-item>
  <grid-item>
    <box border radius="md" padding={3} gap={2}>
      **ARIA Snapshot**
      <box background="surface-tertiary" radius="sm" padding={2}>
        <text size="xs" preserveWhitespace={true}>- heading "Cotton T-shirt" [level=1]{"\n"}- text: $29.99{"\n"}- button "Add to cart"</text>
      </box>
      <caption>检查角色、名称、状态及层级关系。</caption>
    </box>
  </grid-item>
</grid>

此外，DOM Snapshot 可以记录 HTML 结构，但 HTML 发生变化不一定意味着视觉或无障碍语义发生变化。

三种快照解决的是不同的问题。

### 8.2 ARIA Snapshot 实战

假设有以下 HTML：

```html
<fieldset id="ProductColor">

  <legend>Color</legend>

  <label>
    <input type="radio" name="color" checked>
    Black
  </label>

  <label>
    <input type="radio" name="color">
    White
  </label>

</fieldset>
```

测试：

```typescript
await expect(
  page.locator('#ProductColor')
).toMatchAriaSnapshot(`
  - group "Color":
    - radio "Black" [checked]
    - radio "White"
`);
```

如果开发人员后续移除了 fieldset、legend 或正确的 Radio 语义，快照就可能出现差异。

### 8.3 将快照单独存储

也可以将预期结构存储为 `.aria.yml` 文件：

```typescript
await expect(
  page.locator('#ProductColor')
).toMatchAriaSnapshot({
  name: 'product-color.aria.yml'
});
```

更新快照：

```bash
npx playwright test --update-snapshots
```

### 8.4 ARIA Snapshot 应该如何使用？

不要对整个 Shopify 页面无差别地建立严格快照。

因为商品名称、库存、购物车数量、营销文案等经常变化，过大的快照会产生大量无意义的差异。

更推荐针对稳定的公共组件建立快照。

| 组件 | 快照价值 |
|---|---|
| Variant Picker | 高 |
| Tabs | 高 |
| Accordion | 高 |
| Quantity Selector | 高 |
| Cart Drawer 的基础结构 | 高 |
| 整个动态 Collection 页面 | 较低 |

同时注意，Playwright 的 ARIA Snapshot 具有匹配规则，并不等于严格逐节点比较整个浏览器无障碍树。

它也不能证明 NVDA 或 VoiceOver 的实际播报一定正确。

## 9. Baseline：如何处理历史遗留问题？

假设公司已经运营了三年，现有 Shopify 网站累计存在 300 个自动检测问题。

如果现在接入 CI，并直接要求：

```typescript
expect(results.violations).toEqual([]);
```

那么团队可能在完成全部历史整改之前，都无法正常提交代码。

这种情况下，可以引入 **Accessibility Baseline（无障碍基线）**。

它的目标不是允许问题永久存在，而是：

**已有问题逐步整改，新增问题立即拦截。**

<Chart content={{"chartType":"line","xKey":"week","series":[{"dataKey":"legacy","label":"历史遗留问题"},{"dataKey":"allowed","label":"允许的基线上限"}],"yAxisMin":0,"data":[{"week":"第1周","legacy":300,"allowed":300},{"week":"第2周","legacy":260,"allowed":260},{"week":"第3周","legacy":180,"allowed":180},{"week":"第4周","legacy":110,"allowed":110},{"week":"第5周","legacy":45,"allowed":45},{"week":"第6周","legacy":0,"allowed":0}]}}/>
<caption>模拟整改趋势。已经修复的问题应从 Baseline 中移除，防止再次出现。</caption>

### 9.1 三种基线策略

| 策略 | 判断方式 | 推荐程度 |
|---|---|---|
| 总问题数量 | 当前数量不超过历史数量 | 较低 |
| Rule ID | 不允许新增失败规则 | 一般 |
| Violation Fingerprint | 比较具体规则和受影响节点 | 推荐 |

为什么只比较数量不够？

假设本次修复了 10 个颜色对比度问题，却引入了 10 个没有名称的按钮。

总问题数量不变，但实际上产生了新的无障碍缺陷。

因此，应尽可能识别具体问题，而不是仅统计数量。

### 9.2 建立问题指纹

```typescript
import type { AxeResults } from 'axe-core';

export function getFingerprints(results: AxeResults) {
  return results.violations.flatMap(rule =>
    rule.nodes.map(node =>
      JSON.stringify([
        rule.id,
        node.target
      ])
    )
  ).sort();
}
```

可能得到：

```json
[
  "[\"button-name\",[\"#HeaderSearchButton\"]]",
  "[\"color-contrast\",[\".product-price\"]]"
]
```

实际项目还需要按照测试页面、业务状态、浏览器项目分别保存基线，避免不同页面上的相似选择器被误认为同一个问题。

### 9.3 基线记录结构

`tests/baselines/accessibility.json`：

```json
{
  "desktop-chromium/homepage-default": [
    {
      "rule": "button-name",
      "target": ["#HeaderSearchButton"],
      "issue": "A11Y-001",
      "owner": "storefront-team",
      "expiresAt": "2027-01-31"
    }
  ]
}
```

这条记录包含的不只是规则和节点，还包括负责团队、整改任务及到期时间。

### 9.4 新增问题检测

```typescript
import type { AxeResults } from 'axe-core';

type BaselineEntry = {
  rule: string;
  target: unknown;
  issue: string;
  owner: string;
  expiresAt: string;
};

export function findNewViolations(
  results: AxeResults,
  baseline: BaselineEntry[]
) {
  const today = new Date()
    .toISOString()
    .slice(0, 10);

  const allowed = new Set(
    baseline
      .filter(item => item.expiresAt >= today)
      .map(item => JSON.stringify([
        item.rule,
        item.target
      ]))
  );

  return getFingerprints(results)
    .filter(fingerprint => !allowed.has(fingerprint));
}
```

在第 5 节的扫描工具中，可以将零违规断言替换为：

```typescript
const stateKey = `${testInfo.project.name}/${state}`;

const known = baselines[stateKey] ?? [];

const newViolations = findNewViolations(
  results,
  known
);

expect(newViolations).toEqual([]);
```

没有基线记录的新页面，默认仍然要求零自动检测违规。

Playwright 官方无障碍测试文档也介绍了基于规则 ID 和目标选择器建立违规指纹的思路。<Cite ref="turn120024search15"/>

## 10. GitHub Actions：无障碍 CI/CD

### 10.1 Shopify CI 与普通前端项目的区别

普通 Vue 或 React 项目通常可以在 CI 中直接执行：

```bash
npm run build
npm run preview
```

然后由 Playwright 访问 localhost。

但 Shopify Liquid Theme 需要 Shopify 平台进行服务端渲染。

因此，更完整的 CI 流程是：

<box border radius="lg" padding={3} gap={1}>
  {#each [{t:"开发者提交 Pull Request",d:"获取当前提交的 Theme 代码"},{t:"Static Checks",d:"Theme Check、ESLint"},{t:"Preview Deployment",d:"部署当前提交到未发布测试 Theme"},{t:"Playwright + axe-core",d:"访问对应 Theme 预览环境"},{t:"Generate Reports",d:"生成 JSON、HTML、截图及 Trace"},{t:"Quality Gate",d:"检查新增问题及业务测试"},{t:"Merge / Release",d:"通过审查后才允许发布"}] as p,i}
    <box border radius="md" padding={2} gap={1}>**{p.t}**<caption>{p.d}</caption></box>
    {#if i<6}<box align="center"><icon name="arrow-down" color="secondary" size="sm"/></box>{/if}
  {/each}
</box>

特别注意：如果 CI 测试的是线上正式 Theme，而不是当前 PR 对应的预览 Theme，那么即使测试全部通过，也无法证明当前 PR 没有引入问题。

### 10.2 GitHub Actions 配置

创建 `.github/workflows/accessibility.yml`：

```yaml
name: Accessibility Quality Gate

on:
  pull_request:
    branches: [main]

  workflow_dispatch:
    inputs:
      storefront_url:
        description: URL of the matching test theme
        required: true
        type: string

permissions:
  contents: read

jobs:
  theme-check:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Theme Check
        run: npm run lint:theme -- --fail-level error

  accessibility:
    if: github.event_name == 'workflow_dispatch'
    needs: theme-check
    runs-on: ubuntu-latest

    env:
      STOREFRONT_URL: ${{ inputs.storefront_url }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Accessibility tests
        run: npm run test:a11y

      - name: Upload reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: accessibility-report
          path: |
            playwright-report/
            test-results/
          retention-days: 14
```

Playwright 官方 CI 文档支持这种依赖安装、浏览器安装、测试执行和报告归档的基本流程。<Cite ref="turn120024search0"/>

这是一套可以作为起点的分阶段配置：

- 提交 PR 时自动运行 Theme Check。
- 当前提交部署到测试 Theme 后，手动触发动态无障碍测试。
- 后续接入公司的 Theme 预览部署流程，再将动态测试改为每个 PR 自动运行。

这里没有假设你的公司已经具备 Shopify 自动预览部署环境，因此没有直接写入可能修改真实店铺的部署命令。

正式环境应锁定依赖版本，并根据当前 CLI 和 GitHub Actions 版本调整运行环境。

### 10.3 如何实现真正的 PR 质量门禁？

在 GitHub 仓库中配置 Branch Protection 或 Rulesets，设置 Required Status Checks。

GitHub 支持要求指定检查通过后才能合并 PR。<Cite ref="turn518538search4"/>

    <caption>Update product card component</caption>
  </row>
  <divider/>
  {#each [{t:"Theme Check",ok:true},{t:"ESLint",ok:true},{t:"Playwright E2E",ok:true},{t:"Accessibility Quality Gate",ok:false}] as p}
    <row align="center">
      <icon name={p.ok?"check-circle":"x-circle"} color={p.ok?"success":"danger"}/>
      <text size="sm">{p.t}</text>
      <spacer/>
      <caption>{p.ok?"Passed":"Failed"}</caption>
    </row>
  {/each}
  <box background="surface-tertiary" radius="sm" padding={3} gap={1}>
    **合并被阻止**
    <text size="sm">button-name: 新增 Quick Add 按钮缺少 Accessible Name。</text>
  </box>
  <caption>这是完成自动预览部署集成后的目标效果，并非上面手动触发配置已经实现的 PR 动态门禁。</caption>
</box>

在自动预览部署尚未接入前，只应把实际运行于 PR 的检查设为对应的必需检查。

另外，Shopify 测试店铺密码、预览部署凭证等应通过安全的 Secrets 管理机制注入，不能直接写进 YAML 或提交到 Git。

## 12. 建立无障碍 Design System

如果你只负责修复代码，却不参与设计规范制定，同一种问题很可能在下一份设计稿中再次出现。

因此，团队需要建立统一的无障碍设计标准。

### 12.1 Accessibility Design Tokens

例如统一定义：

```css
:root {
  /* Focus */
  --focus-color: #005fcc;
  --focus-width: 2px;
  --focus-offset: 3px;

  /* Touch target */
  --control-min-size: 44px;

  /* Text */
  --text-primary: #222222;
  --text-secondary: #595959;
  --text-error: #b42318;

  /* Motion */
  --motion-duration: 200ms;
}

:focus-visible {
  outline: var(--focus-width) solid var(--focus-color);
  outline-offset: var(--focus-offset);
}

@media (prefers-reduced-motion: reduce) {
  :root {
    --motion-duration: 0ms;
  }
}
```

这些是建议的基础 Token，不是说使用这些数值就自动满足 WCAG。

例如焦点颜色是否合适，还需要结合实际背景和组件状态进行验证。

### 12.2 统一组件状态

每个交互组件的设计稿都应该考虑完整的状态，而不仅仅是 Default 和 Hover。

<box border radius="lg" padding={3} gap={3}>
  **Button Component**
  <grid columns={2} gap={3}>
    {#each [{t:"Default",bg:"#333333",fg:"#FFFFFF",label:"Add to cart"},{t:"Hover",bg:"#505050",fg:"#FFFFFF",label:"Add to cart"},{t:"Focus",bg:"#333333",fg:"#FFFFFF",label:"Add to cart"},{t:"Active",bg:"#111111",fg:"#FFFFFF",label:"Add to cart"},{t:"Disabled",bg:"#DDDDDD",fg:"#595959",label:"Sold out"},{t:"Loading",bg:"#555555",fg:"#FFFFFF",label:"Adding…"}] as p}
      <grid-item>
        <box gap={1}>
          <caption>{p.t}</caption>
          <box border={{size:2,color:p.t==="Focus"?"#005fcc":"transparent"}} radius="md" padding={1}>
            <box background={p.bg} theme="light" radius="sm" padding={3} align="center">
              <row align="center" gap={2}>
                {#if p.t==="Loading"}<icon name="loader" size="sm" color={p.fg}/>{/if}
                <text size="sm" color={p.fg}>{p.label}</text>
              </row>
            </box>
          </box>
        </box>
      </grid-item>
    {/each}
  </grid>
  <caption>不同组件状态不仅需要视觉设计，还需要明确对应的语义与交互行为。</caption>
</box>

| 组件状态 | 技术实现重点 |
|---|---|
| Default | 正确的原生语义 |
| Hover | 不作为唯一操作方式 |
| Focus | 明确可见的焦点指示 |
| Selected | checked、aria-selected 等适当状态 |
| Disabled | disabled 或正确实现 aria-disabled |
| Loading | 重复提交保护及状态通知 |
| Error | 错误文字与控件关联 |
| Expanded | 展开状态及内容同步 |

### 12.3 为公共组件建立无障碍契约

例如团队维护一个 Modal 组件，不应该只提供 CSS 和 JavaScript，还应该明确它的无障碍接口及行为。

```typescript
interface AccessibleDialogOptions {
  initialFocus?: HTMLElement;

  returnFocus?: HTMLElement;

  closeOnEscape?: boolean;

  closeOnOutsideClick?: boolean;

  onOpen?: () => void;

  onClose?: () => void;
}
```

同时在组件文档中定义：

| 契约 | 要求 |
|---|---|
| Semantic | 具有 dialog 语义及名称 |
| Initial Focus | 打开时焦点进入合理位置 |
| Focus Isolation | 背景不可意外访问 |
| Keyboard | 提供适当的键盘关闭机制 |
| Restoration | 关闭时恢复合理焦点 |
| Lifecycle | 不依赖装饰性动画完成核心行为 |
| Testing | 包含 axe、键盘及人工辅助技术测试 |

这样后续开发 Quick Add、Size Guide、Search Modal、Cart Drawer 时，都可以复用同一个经过验证的基础组件。

### 12.4 Shopify Theme 推荐公共模块

```text

├── accessible-dialog.js
├── accessible-disclosure.js
├── accessible-tabs.js
├── accessible-carousel.js
├── accessible-combobox.js
├── focus-manager.js
├── live-announcer.js
├── cart-controller.js
└── accessibility.css

snippets/

```

把它们沉淀成团队基础设施，比每次开发业务时重新实现一套焦点管理和 ARIA 逻辑更容易维护。

  <box background="surface-tertiary" radius="full" height={5}>
    <box background="#39866B" height={5} radius="full" width={`${prDone.filter(Boolean).length/prChecks.length*100}%`}/>
  </box>
  {#each prChecks as c,i}
    <checkbox checked={prDone[i]} onChange={v=>setPrDone(old=>old.map((x,j)=>j===i?v:x))} lineThrough={prDone[i]}>{c}</checkbox>
  {/each}
  <divider/>
  <button block variant="outline" color="secondary" onClick={()=>GenUI.copy("## Accessibility Checklist\n\n"+prChecks.map((c,i)=>(prDone[i]?"- [x] ":"- [ ] ")+c).join("\n"))}><icon name="copy" size="sm"/> 复制 Markdown PR 模板</button>
</card>

对于不适用于当前 PR 的检查项，应标记为 N/A 并说明原因，而不是为了完成 Checklist 随意勾选。

### 13.1 Definition of Done

团队可以进一步将无障碍纳入需求的完成标准。

一个组件只有在功能实现、视觉验收、键盘操作、自动检测和适用的屏幕阅读器测试全部完成后，才被认为真正开发完成。

这样可以避免无障碍整改永远被安排到下一个 Sprint。

即使你的 Theme 本身实现得非常好，安装第三方 App 后，仍然可能引入无障碍问题。

### 14.1 常见第三方 App 问题

| App 类型 | 常见风险 |
|---|---|
| 评论 App | 星级无名称、筛选不可操作 |
| 客服 App | 无法通过键盘关闭 |
| Cookie Banner | 模态焦点错误、按钮名称缺失 |
| Upsell App | 弹窗抢夺焦点 |
| 订阅 App | 购买方式缺少分组语义 |
| 邮件营销 App | 表单标签及错误反馈缺失 |
| 商品定制 App | Canvas 或拖拽缺少替代操作 |

### 14.2 为什么不能简单地 exclude 第三方 App？

例如：

```typescript
new AxeBuilder({ page })
  .exclude('#third-party-app')
  .analyze();
```

这可以让报告看起来更干净，但用户实际访问的网站并没有得到修复。

在组件级测试中，临时排除某个不属于本次测试范围的模块可以合理；在完整网站合规审计中，不能因为代码来自第三方，就将用户实际遇到的障碍视为不存在。

### 14.3 第三方 App 整改策略

建议依次考虑：

1. 检查 App 是否已有无障碍配置。
2. 使用官方支持的样式及组件定制接口。
3. 向 App 开发商提交详细复现报告。
4. 对无法及时修复的问题建立整改记录及替代方案。
5. 对严重阻断购买流程且长期无法修复的 App，评估替换或移除。

对于 cross-origin iframe 或封闭的 Shadow DOM，Theme JavaScript 可能无法直接修改内部结构。

不建议长期依靠 MutationObserver 强行修改第三方 App 的 ARIA 属性，因为这样可能与 App 自己的状态管理冲突。

同样，Accessibility Overlay 或无障碍辅助工具栏，也不能代替底层语义、键盘交互及真实业务流程的整改。

## 15. 商家配置与 Shopify Theme 的特殊挑战

Shopify Theme 并不是一套固定不变的页面。

商家可以在 Theme Editor 中修改颜色、图片、Section、Block、文字内容及动画配置。

因此，同一套 Theme 可能在一种配置下正常，在另一种配置下出现无障碍问题。

### 15.2 Theme 配置测试矩阵

| 商家配置 | 需要检查的内容 |
|---|---|
| Color Scheme | 文字、按钮和状态对比度 |
| Logo | 图片替代文本、链接名称 |
| Image Banner | 文字与图片背景对比度 |
| Slideshow | 自动播放与暂停 |
| Rich Text | 标题层级、链接、图片 alt |
| Custom Liquid | 任意自定义代码的风险 |
| App Block | 第三方组件无障碍表现 |

| Shopify Markets | 币种、配送和地区选择 |

**Theme 无障碍与实际店铺无障碍并不是同一个概念。**

### 16.1 WCAG 2.2 AA 是怎样的目标？

需要理解，Level AA 并不是只检查 AA 准则，而是需要满足所有适用的 Level A 和 Level AA 准则。

还应考虑完整页面、完整业务流程、受支持的无障碍技术以及非干扰等合规要求。

例如：

```text
Homepage          通过
Collection        通过
Product           通过
Cart              通过
Checkout          无法通过键盘完成支付
```

不能仅仅因为大部分页面通过，就宣称整个购买流程符合 WCAG 2.2 AA。

### 16.2 正式评估报告的组成

| 章节 | 内容 |
|---|---|
| Executive Summary | 评估结果与主要风险 |
| Scope | 店铺、页面及功能范围 |
| Conformance Target | 目标 WCAG 版本和级别 |
| Methodology | 测试方法、工具及环境 |
| Representative Sample | 页面和状态样本 |
| Findings | 具体准则及问题 |
| Remediation Plan | 修复方式、负责人和优先级 |
| Verification | 修复后的验证结果 |
| Limitations | 未测试范围及评估限制 |

### 16.3 ADA 与 WCAG 的关系

这是整套课程开始时学习过的重要概念，现在再次强调。

| 项目 | 性质 |
|---|---|
| ADA | 美国残障人士权利相关法律 |
| WCAG | Web 内容无障碍技术标准 |
| WAI-ARIA | 无障碍语义技术规范 |
| APG | 组件设计和交互实现指导 |
| WCAG-EM | 无障碍合规评估方法 |
| axe-core | 自动化检测工具 |

**不能将工具测试通过、WCAG 技术符合性和 ADA 法律合规直接画等号。**

对于跨境电商企业，可以将 WCAG 2.2 AA 作为内部技术整改目标，但具体法律适用范围、合规义务以及诉讼风险，需要结合实际业务和适用法律进行专业评估。

## 17. 如何持续维护无障碍质量？

建议将无障碍检查分布在日常开发、版本发布和运营过程中。

| 周期 | 建议任务 |
|---|---|
| 每次代码提交 | 静态检查 |
| 每次 PR | axe、组件交互测试、Code Review |
| 每次版本发布 | 核心购买流程回归测试 |
| 每周 | 关键页面及动态状态扫描 |
| 每月 | 屏幕阅读器抽查、历史问题跟踪 |
| 每季度 | 系统性人工评估 |
| 安装或升级 App 后 | 第三方组件专项测试 |
| 大型营销活动上线前 | 活动页面无障碍检查 |
| Theme 大版本升级后 | 完整回归测试 |

这里的周期是建议的团队管理方案，并不是 ADA 或 WCAG 统一规定的检测频率。

## 三、前端无障碍开发的十大原则

这是我认为整套课程中最值得长期记住的内容。

| 原则 | 核心思想 |
|---|---|
| 01. Native First | 优先使用原生 HTML 元素 |
| 02. Semantic First | 先确定业务语义，再设计交互 |
| 03. ARIA Is Not Behavior | ARIA 不会自动实现交互行为 |
| 04. Keyboard First | 所有适用功能都应支持键盘 |
| 05. Focus Is a State | 焦点是必须管理的组件状态 |
| 06. State Synchronization | 数据、UI、ARIA 和交互状态保持一致 |
| 07. Respect User Preferences | 尊重缩放、颜色和减少运动偏好 |
| 08. Announce Meaningful Changes | 通知重要业务变化，而不是所有 DOM 变化 |
| 09. Test Real User Flows | 测试完整任务，而不只是孤立页面 |
| 10. Accessibility by Design | 从设计开始考虑无障碍，而不是事后补救 |

其中第 5 条和第 6 条，对于 Shopify Theme 开发尤其重要，因为 Section Rendering 会频繁替换 DOM，而 Variant、Cart、Collection 又涉及复杂的业务状态变化。

## 六、结课后的实践方向

考虑到你之前已经系统学习了 Shopify Theme 架构、数据模型、Dawn 源码、SEO 和网站性能优化，我认为接下来不必急着继续学习更多零散的无障碍理论。

更有价值的是将这些知识沉淀为实际工程成果。

| 实践项目 | 价值 |
|---|---|
| Shopify Accessibility Component Library | 建立可复用的无障碍组件库 |
| Shopify Accessibility Test Suite | 建立完整的自动化回归测试体系 |
| Shopify Theme Accessibility Guidelines | 沉淀公司内部开发规范 |
| Dawn Accessibility Audit | 结合源码进行真实整改实战 |
| Storefront Quality Dashboard | 统一管理性能、SEO 和无障碍质量 |

其中，我最推荐优先开发一套 **Shopify Theme 无障碍基础组件库**，包含 Modal、Drawer、Tabs、Accordion、Combobox、Carousel、Focus Manager 和 Live Announcer。

这些都是你在日常 Shopify 开发中能够反复使用的基础设施。

至此，整套 ADA 网站无障碍课程正式结束。

希望你以后理解的 Accessibility，不再只是 alt、aria-label、tabindex，也不再只是 Lighthouse 里的一个评分，而是一套与前端架构、组件设计、业务可靠性和用户体验紧密关联的工程能力。
