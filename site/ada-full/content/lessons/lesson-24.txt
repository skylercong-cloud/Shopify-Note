不同类型的问题，需要不同的检测方式。

| 无障碍问题 | 自动检测 | 人工检测 |
|---|---|---|

1. 打开需要检测的 Shopify 页面。

### 2.2 Accessibility Score 是如何计算的？

Lighthouse 的无障碍评分与性能评分存在一个很大的区别。

无障碍评分基于各个适用且参与评分的 Audit 的加权平均值。每项 Audit 基本采用通过或失败的二元评分，而不是根据通过的元素比例给予部分分数。

人工检查项以及部分最佳实践检查项不参与评分。<Cite ref="turn743735view0"/>

计算公式可以简化为：

\[
Score=100\times\frac{\sum w_i s_i}{\sum w_i}
\]

其中：

| 变量 | 含义 |
|---|---|
| \(w_i\) | 当前 Audit 的权重 |
| \(s_i\) | 通过为 1，失败为 0 |
| Score | 最终 Accessibility Score |

### 2.4 为什么修复了很多按钮，分数却没有变化？

假设页面上有 100 个按钮，其中 10 个按钮没有 Accessible Name。

你修复了其中 9 个，但仍剩下一个。

| 修复情况 | Button Name Audit |
|---|---|
| 10 个错误按钮 | Fail |
| 5 个错误按钮 | Fail |
| 1 个错误按钮 | Fail |
| 全部修复 | Pass |

只要还有一个受该规则检测的按钮不合格，这项 Audit 就可能仍然是失败状态。

因此，无障碍评分不适合用来直接衡量问题数量或者整改工作量。

### 2.5 Lighthouse 100 分是否意味着满足 ADA？

**不意味着，也不代表网站已经符合 WCAG 2.2 AA。**

例如一个网站可能获得 100 分，但仍存在以下问题：

| 实际问题 | Lighthouse 可能遗漏的原因 |
|---|---|
| 商品图片 alt 全部写成 image | 属性存在，但内容没有意义 |
| Cart Drawer 无法通过 Esc 退出 | 需要操作测试 |
| Variant Picker 切换后焦点丢失 | 需要动态状态测试 |
| 加购成功却没有有效通知 | 需要结合业务与辅助技术 |
| 商品描述中重要信息只依赖颜色 | 需要理解内容 |
| 用户无法完成结账 | 需要测试完整流程 |

可以将 Lighthouse 100 分作为内部质量目标之一，但不能将它作为 ADA 合规证明。

## 3. axe-core：无障碍检测的核心引擎

Lighthouse 和 axe 并不是两个完全独立的检测体系。

Lighthouse 的不少 Accessibility Audit 建立在 axe-core 的检测能力之上，但 Lighthouse 并不等同于运行全部 axe-core 规则。

axe-core 是 Deque 开源的 JavaScript 无障碍检测引擎。

### 3.1 axe-core 检测的是源码还是运行后的页面？

主要检测当前运行状态下的页面 DOM、样式、可访问名称及语义关系等信息。

例如 Shopify 服务端返回：

```liquid
<button>
  {% render 'icon-cart' %}
</button>
```

axe 实际检测的是 Liquid 渲染、JavaScript 执行之后的页面：

```html
<button>
  <svg aria-hidden="true">
    ...
  </svg>
</button>
```

因此 axe 不需要理解 Shopify Liquid 模板本身。

它关心的是最终生成的页面是否存在无障碍问题。

这也是为什么仅仅通过代码审查无法替代浏览器中的实际检测。

### 3.2 Rule 与 Check 的区别

axe-core 的规则系统主要包含 Rule 和 Check。

例如检查按钮是否具有 Accessible Name 的规则：

```text
Rule: button-name
```

其内部可以包含多个检查条件，例如按钮是否具有有效文本内容、aria-label、aria-labelledby 等。

在 axe-core 的结果中，Check 被分为以下三种逻辑组合：

| 类型 | 含义 |
|---|---|
| `any` | 至少一个 Check 必须通过 |
| `all` | 所有 Check 都必须通过 |
| `none` | 所有这些 Check 都必须不匹配 |

所以检测失败并不意味着需要修复报告中列出的每一个候选条件。

例如：

```html
<button aria-label="Search">
  <svg aria-hidden="true"></svg>
</button>
```

已经具备有效的 Accessible Name，就没有必要为了通过检查，再同时添加 title 和 aria-labelledby。

### 3.3 axe Rule 与 WCAG Success Criterion 的关系

例如：

```javascript
{
  id: 'button-name',
  impact: 'critical',
  tags: [
    'cat.name-role-value',
    'wcag2a',
    'wcag412'
  ]
}
```

可以理解为：

| 字段 | 含义 |
|---|---|
| `button-name` | axe 自己的规则标识 |
| `critical` | 工具给出的影响等级 |
| `wcag2a` | WCAG 2 系列 Level A 标签 |
| `wcag412` | WCAG 4.1.2 Name, Role, Value |

但必须注意：**axe Rule 不等于 WCAG 准则。**

一个 WCAG 准则可能对应多个 axe Rule，一个 Rule 也可能关联多个准则。有些规则属于最佳实践，不直接对应 WCAG 合规失败。

### 4.1 Incomplete 为什么特别重要？

例如某段白色文字位于商品营销图片上方。

<box background="#7F8588" radius="md" padding={4} theme="dark">
  <svg viewBox="0 0 320 140" width="100%">
    <defs>
      <linearGradient id="banner24">
        <stop offset="0%" stopColor="#41484B"/>
        <stop offset="55%" stopColor="#AAAAAA"/>
        <stop offset="100%" stopColor="#E9E1D3"/>
      </linearGradient>
    </defs>
    <rect width="320" height="140" rx="5" fill="url(#banner24)"/>
    <path d="M0 140 L120 12 L230 140 Z" fill="#A3A9A8" opacity=".6"/>
    <text x="160" y="65" textAnchor="middle" fill="white" fontSize="25" fontWeight="600">Summer Sale</text>
    <text x="160" y="92" textAnchor="middle" fill="white" fontSize="13">Discover the collection</text>
  </svg>
</box>

文字背景存在图片、渐变或复杂图层时，检测工具不一定能够准确确定实际颜色对比度。

这时结果可能进入 Incomplete，需要人工确认。

所以：

```javascript
results.violations.length === 0
```

仅仅意味着没有检测到确定的规则失败，而不是所有无障碍检查都已经通过。

对于正式审计，Incomplete 应当逐项记录人工检查结果，不能直接忽略。

### 4.2 axe 的四种影响等级

| Impact | 含义 |
|---|---|
| Critical | 极严重，可能阻断关键操作 |
| Serious | 严重影响访问体验 |
| Moderate | 中等程度的访问障碍 |
| Minor | 相对较小的影响 |

注意，这不是 WCAG A、AA、AAA 的划分方式，也不是 ADA 法律风险评级。

实际项目中的修复优先级还应考虑问题出现频率、影响页面范围以及是否阻断购物流程。

## 5. axe DevTools 浏览器插件

对于日常 Shopify Theme 开发，我建议在浏览器中安装 axe DevTools。

它比 Lighthouse 更适合针对具体组件进行无障碍问题定位。

官方地址：[axe DevTools](https://www.deque.com/axe/devtools/)

不同版本和套餐的扫描功能有所区别，但基本的规则检测与问题定位是相同的使用思路。

### 5.2 正确理解 How to fix

检测工具可能给出多种修复方式。

例如按钮缺少名称，工具可能提示：

- 添加有效文本。
- 添加 aria-label。
- 添加有效的 aria-labelledby。
- 使用其他能够提供名称的机制。

不是要求你将所有方案都实现一遍，而是应该结合第 13 课的 Accessible Name 计算规则，选择最合理的一种。

对于纯图标搜索按钮：

```html
<button
  type="button"
  aria-label="Search"
>
  <svg aria-hidden="true" focusable="false">
    ...
  </svg>
</button>
```

就已经是很合理的实现。

### 6.2 WAVE 的报告分类

| 分类 | 作用 |
|---|---|
| Errors | 检测出的无障碍错误 |
| Contrast Errors | 文字颜色对比度问题 |
| Alerts | 需要进一步判断的问题 |
| Features | 图片替代文本、表单标签等特征 |
| Structure | 标题、列表、Landmark 等结构 |
| ARIA | 页面中使用的 ARIA 信息 |

需要注意，绿色 Features 并不代表相关功能一定正确。

例如一张图片存在 alt 属性，WAVE 可以标记它具有替代文本，但仍需要人工判断文本是否准确。

对于开发中的 Shopify Theme、密码保护店铺以及动态弹窗，优先考虑 WAVE 浏览器扩展，而不是只使用在线 URL 检测。扩展更适合分析当前浏览器中的页面状态。<Cite refs={["turn464807search18","turn464807search29"]}/>

## 8. Chrome DevTools：Accessibility Tree 深入调试

前面第 3 课和第 13 课分别介绍过 Accessibility Tree 与 Accessible Name。

现在我们从实际调试角度，将它们结合起来。

Chrome DevTools 的 Elements 面板可以查看 Accessibility Tree、ARIA 属性以及浏览器计算后的无障碍属性，也支持查看完整页面的无障碍树。<Cite ref="turn464807search2"/>

### 8.1 HTML Attribute 与 Computed Property 的区别

假设页面有以下代码：

```html
<button
  aria-label="Shopping cart"
  aria-labelledby="cart-label"
  aria-describedby="cart-count"
>
  <svg aria-hidden="true"></svg>
</button>

<span id="cart-label" hidden>
  View bag
</span>

<span id="cart-count" hidden>
  3 items
</span>
```

如果只检查 DOM 属性，你可能认为按钮名称是 Shopping cart。

但浏览器实际计算的 Accessible Name 可能是 View bag，因为有效的 aria-labelledby 在这里具有更高优先级。

<grid columns={2} gap={3}>
  <grid-item>
    <box border radius="md" padding={3} gap={2}>
      **DOM Attributes**
      <divider/>
      <caption>aria-label</caption>
      <text size="sm">Shopping cart</text>
      <caption>aria-labelledby</caption>
      <text size="sm">cart-label</text>
      <caption>aria-describedby</caption>
      <text size="sm">cart-count</text>
    </box>
  </grid-item>
  <grid-item>
    <box border radius="md" padding={3} gap={2}>
      **Computed Properties**
      <divider/>
      <caption>Role</caption>
      <text size="sm">button</text>
      <caption>Name</caption>
      <text size="sm" weight="medium">View bag</text>
      <caption>Description</caption>
      <text size="sm">3 items</text>
    </box>
  </grid-item>
</grid>

这就是为什么在排查无障碍名称问题时，不应该只看 HTML 上写了什么属性，还需要观察浏览器最终计算出了什么。

### 8.2 如何查看元素的 Accessible Name？

操作步骤：

1. 使用 Chrome DevTools 选中目标 DOM 元素。
2. 找到 Accessibility 面板。
3. 查看 Computed Properties。
4. 展开 Name，检查其来源。
5. 查看 Role、Description、Focusable、Expanded 等状态。
6. 对照实际业务行为，判断计算结果是否正确。

## 9. 使用 JavaScript 直接调用 axe-core

对于前端开发工程师而言，只会使用浏览器插件是不够的。

我们还应该掌握如何通过代码运行 axe-core、获取结构化结果，并进一步接入自己的开发工具。

这也是第 26 课工程化自动检测的基础。

### 9.1 安装 axe-core

```bash
npm install -D axe-core
```

如果你的 Shopify Theme 项目使用 Vite、Webpack 等构建工具，可以在开发环境中引入 axe-core。

```javascript
import axe from 'axe-core';

const results = await axe.run(document);

console.log(results);
```

建议只在开发或测试环境中引入检测代码，不需要将 axe-core 打包进正式面向消费者的生产脚本。

### 9.2 只检测 WCAG 2.2 A 和 AA 相关规则

```javascript
const results = await axe.run(document, {
  runOnly: {
    type: 'tag',
    values: [
      'wcag2a',
      'wcag2aa',
      'wcag21a',
      'wcag21aa',
      'wcag22a',
      'wcag22aa'
    ]
  }
});
```

这些 Tag 用于筛选对应版本及级别的自动检测规则，具体支持情况取决于安装的 axe-core 版本。

注意，指定 WCAG 2.2 AA 相关规则，并不意味着 axe 会完整检查 WCAG 2.2 AA 的全部准则。

### 9.3 只检测某个组件

例如，只检测已经打开的购物车抽屉：

```javascript
const results = await axe.run('#CartDrawer');

console.log(results.violations);
```

也可以排除指定区域：

```javascript
const results = await axe.run({
  include: [['#MainContent']],
  exclude: [['#DevelopmentToolbar']]
});
```

这种方式适合开发阶段的组件级排查。

但是正式审计时，不能为了获得零错误，就随意排除第三方插件、Header 或 Footer。组件之间的交互问题也需要通过整页检测发现。

### 9.4 axe.run() 的返回数据结构

```javascript
{
  testEngine: {
    name: 'axe-core',
    version: '...'
  },

  url: 'https://example.com/products/shirt',

  timestamp: '...',

  violations: [],
  incomplete: [],
  passes: [],
  inapplicable: []
}
```

假设检测到一个按钮没有 Accessible Name，简化后的结果可能是：

```javascript
{
  id: 'button-name',

  impact: 'critical',

  description: 'Ensure buttons have discernible text',

  help: 'Buttons must have discernible text',

  helpUrl: '...',

  tags: [
    'wcag2a',
    'wcag412'
  ],

  nodes: [
    {
      target: ['#HeaderSearchButton'],

      html: '<button id="HeaderSearchButton">...</button>',

      failureSummary: '...',

      any: [],
      all: [],
      none: []
    }
  ]
}
```

这是根据官方 API 数据结构简化的教学示例。实际返回的 Check 信息、目标选择器以及相关节点可能更加复杂。<Cite ref="turn464807search1"/>

### 9.5 将检测结果转换成易读的表格

```javascript
const results = await axe.run(document);

const issues = results.violations.flatMap(rule =>
  rule.nodes.map(node => ({
    rule: rule.id,
    impact: node.impact || rule.impact,
    selector: JSON.stringify(node.target),
    html: node.html,
    wcag: rule.tags
      .filter(tag => /^wcag\d{3,}$/.test(tag))
      .join(', '),
    reason: node.failureSummary,
    reference: rule.helpUrl
  }))
);

console.table(issues);
```

## 10. 常见 axe Rule 与 Shopify 修复实战

接下来学习日常 Shopify 开发中比较值得关注的检测规则。

### 10.1 button-name：按钮缺少名称

**常见位置：** Header 图标、关闭按钮、轮播箭头、购物车删除按钮。

错误：

```html
<button>
  <svg aria-hidden="true"></svg>
</button>
```

修复：

```html
<button type="button" aria-label="Close shopping cart">
  <svg aria-hidden="true"></svg>
</button>
```

不要简单地给所有图标按钮设置 `aria-label="button"`，因为这并没有说明按钮的实际功能。

### 10.2 link-name：链接缺少名称

错误：

```html
<a href="/collections/sale">
  <img src="sale-banner.jpg" alt="">
</a>
```

修复：

```html
<a href="/collections/sale">
  <img
    src="sale-banner.jpg"
    alt="Shop the summer sale"
  >
</a>
```

当图片是链接的唯一内容时，alt 应能够表达链接的用途。

### 10.3 image-alt：图片缺少替代文本

错误：

```liquid
<img src="{{ product.featured_image | image_url: width: 600 }}">
```

修复：

```liquid
{{
  product.featured_image
  | image_url: width: 600
  | image_tag: alt: product.featured_image.alt
}}
```

这里仍然需要在 Shopify 后台维护准确的图片 alt。

装饰图片可以使用空 alt，但重要商品图片不能为了通过检测而全部设置 `alt=""`。

### 10.4 label：表单字段缺少标签

错误：

```html
<input
  type="email"
  placeholder="Enter your email"
>
```

修复：

```html
<label for="NewsletterEmail">
  Email address
</label>

<input
  id="NewsletterEmail"
  type="email"
  name="email"
  autocomplete="email"
  placeholder="you@example.com"
>
```

虽然部分浏览器可能从 placeholder 计算出名称，部分检测也可能通过，但 placeholder 不能代替稳定、清晰的表单标签。

### 10.5 aria-hidden-focus：隐藏区域仍包含可聚焦元素

这是 Shopify 自定义 Drawer 和 Carousel 中非常典型的问题。

错误：

```html
<div class="cart-drawer" aria-hidden="true">
  <button>Close cart</button>
  <a href="/cart">View cart</a>
</div>
```

修复方案之一：

```html
<div class="cart-drawer" inert>
  <button>Close cart</button>
  <a href="/cart">View cart</a>
</div>
```

打开时：

```javascript
drawer.inert = false;
```

关闭时：

```javascript
trigger.focus();

drawer.inert = true;
```

如果原来还有 `aria-hidden="true"`，也必须在打开时移除或正确同步。

`inert` 负责交互隔离，但不会自行将 Drawer 从视觉上隐藏，也不能代替完整的模态弹窗管理。

### 10.6 aria-valid-attr-value：ARIA 属性值不合法

错误：

```html
<button aria-expanded="yes">
  Filters
</button>
```

修复：

```html
<button aria-expanded="false">
  Filters
</button>
```

JavaScript 同步状态：

```javascript
button.setAttribute(
  'aria-expanded',
  String(isOpen)
);
```

### 10.7 aria-required-children：缺少必需的子角色

错误：

```html
<div role="tablist">
  <button>Description</button>
  <button>Reviews</button>
</div>
```

修复：

```html
<div role="tablist" aria-label="Product information">

  <button
    role="tab"
    aria-selected="true"
    aria-controls="description-panel"
    id="description-tab"
  >
    Description
  </button>

  <button
    role="tab"
    aria-selected="false"
    aria-controls="reviews-panel"
    id="reviews-tab"
    tabindex="-1"
  >
    Reviews
  </button>

</div>
```

然后还需要实现对应 Tabpanel 以及第 17 课学习的键盘交互。

仅补充 `role="tab"` 可以解决某项结构规则，却不代表整个 Tabs 组件已经实现无障碍。

### 10.8 color-contrast：文字颜色对比度不足

{@body const [contrastFg24,setContrastFg24]=DIL.useState("#999999")}
{@body const [contrastBg24,setContrastBg24]=DIL.useState("#FFFFFF")}
{@body const [largeText24,setLargeText24]=DIL.useState(false)}

在 Shopify 网站中，最容易出现对比度不足的地方通常包括：

| 位置 | 常见问题 |
|---|---|
| 商品原价 | 灰色过浅 |
| Placeholder | 为了视觉弱化而降低对比度 |
| Footer | 灰色文字与深色背景不匹配 |
| 商品库存 | 浅绿色文字 |
| Filter Count | 数量颜色太浅 |
| Announcement Bar | 商家自定义颜色组合 |
| Banner | 白色文字覆盖浅色图片 |

修复时最好直接修改 Theme 的颜色变量或 Color Scheme 配置，而不是在几十个组件中分别硬编码颜色。

这样可以从根源上解决同类问题。

### 10.9 其他值得掌握的规则

| axe Rule | 检测内容 | 可能涉及的 WCAG |
|---|---|---|
| `button-name` | 按钮名称 | 4.1.2 |
| `link-name` | 链接名称 | 2.4.4、4.1.2 |
| `image-alt` | 图片替代文本 | 1.1.1 |
| `label` | 表单控件名称 | 1.3.1、4.1.2 等 |
| `color-contrast` | 文字对比度 | 1.4.3 |
| `aria-hidden-focus` | 隐藏区域焦点 | 4.1.2 |
| `aria-required-attr` | 必需的 ARIA 属性 | 4.1.2 |
| `aria-allowed-attr` | 角色允许的属性 | 4.1.2 |
| `nested-interactive` | 交互控件非法嵌套 | 4.1.2 |
| `html-has-lang` | 页面语言声明 | 3.1.1 |
| `heading-order` | 标题层级顺序 | 通常属于最佳实践 |
| `landmark-one-main` | 主要内容地标 | 通常属于最佳实践 |
| `region` | 内容是否位于地标内 | 通常属于最佳实践 |

完整规则列表可以查看 [axe-core Rule Descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)。

实际使用时，应以项目安装版本返回的 Rule Tags 和文档为准。

特别注意：最佳实践规则失败不一定直接构成 WCAG 违规，但仍然可能值得修复。

## 11. 如何检测动态组件？

这是本节课对 Shopify 开发最有价值的部分。

很多网站在首次加载时检测结果非常好，但是用户打开 Mega Menu、Cart Drawer 或 Quick Add Modal 后，会出现大量新的无障碍问题。

### 11.1 页面检测不等于页面状态检测

<box border radius="lg" padding={3} gap={3}>
  <row align="center">
    **Collection Page**
    <spacer/><caption>同一个 URL</caption>
  </row>
  <grid columns={2} gap={2}>
    {#each [{t:"初始页面",n:0,i:"layout-grid"},{t:"Mega Menu 展开",n:3,i:"menu"},{t:"Filter Drawer 打开",n:5,i:"sliders-horizontal"},{t:"Quick Add Modal 打开",n:2,i:"layers"},{t:"Cart Drawer 打开",n:4,i:"shopping-bag"},{t:"表单错误状态",n:2,i:"alert-circle"}] as p}
      <grid-item>
        <box border radius="md" padding={3} gap={2}>
          <icon name={p.i} size="xl"/>
          **{p.t}**
          <title size="xl" color={p.n?"danger":"success"}>{p.n}</title>
          <caption>模拟违规节点条目数</caption>
        </box>
      </grid-item>
    {/each}
  </grid>
  <caption>同一个页面在不同业务状态下，检测结果可能完全不同。以上数量为教学数据。</caption>
</box>

如果只运行一次：

```javascript
await axe.run(document);
```

检测的是当时的页面状态，并不会自动完成打开菜单、选择商品、加购、提交错误表单等操作。

所以，必须主动建立 **Page State Testing（页面状态检测）** 的概念。

### 11.2 使用浏览器插件检测动态状态

以 Cart Drawer 为例：

1. 在 PDP 选择有效 Variant。
2. 点击 Add to cart。
3. 等待 Cart Drawer 打开。
4. 使用 axe DevTools 重新扫描页面。
5. 修改商品数量，再扫描。
6. 删除全部商品，在 Empty Cart 状态再次扫描。

检测 Modal 时，除了扫描内部元素，还应该进行整页扫描，判断背景区域是否存在不合理的隐藏与焦点状态。

### 11.3 使用 Playwright + axe-core

安装：

```bash
npm install -D @axe-core/playwright
```

代码：

```javascript
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('cart drawer accessibility', async ({ page }) => {
  await page.goto('/products/cotton-tshirt');

  await page.getByRole('button', {
    name: 'Add to cart',
    exact: true
  }).click();

  const drawer = page.getByRole('dialog', {
    name: 'Your cart'
  });

  await expect(drawer).toBeVisible();

  const results = await new AxeBuilder({ page })
    .withTags([
      'wcag2a',
      'wcag2aa',
      'wcag21a',
      'wcag21aa',
      'wcag22a',
      'wcag22aa'
    ])
    .analyze();

  expect(results.violations).toEqual([]);
});
```

这个例子与普通自动化测试的区别是：先通过 Playwright 让页面进入指定业务状态，再通过 axe 执行无障碍规则扫描。

实际项目中还应等待 Cart Drawer 完成渲染、相关异步请求结束，并单独验证焦点限制和恢复行为。

不要依赖固定的：

```javascript
await page.waitForTimeout(1000);
```

更推荐等待明确的业务状态。

关于完整的 Playwright、axe-core 和 CI/CD 集成，我们将在第 26 课详细学习。

## 12. Shopify 网站完整无障碍审计方案

假设现在需要对公司的 Shopify 网站进行一次 WCAG 2.2 AA 技术审计。

不建议无计划地打开几十个商品页面逐一运行 Lighthouse。

更合理的方式是按照模板、组件、业务状态和完整流程进行抽样。

W3C 的 WCAG-EM 评估方法也强调明确评估范围、选择有代表性的样本、评估以及报告结果。<Cite ref="turn743735search2"/>

### 12.1 第一层：页面模板检测

| 页面类型 | 检测重点 |
|---|---|
| Homepage | Banner、轮播、营销模块 |
| Collection | 筛选、排序、商品卡片 |
| Product | Variant、价格、图库、数量 |
| Search | 搜索结果、无结果状态 |
| Cart | 数量修改、删除、结算 |
| Checkout | 地址、配送、支付、确认 |
| Blog / Article | 标题、富文本、图片 |
| Contact | 表单、校验、错误反馈 |
| Account | 登录、注册、密码恢复 |
| Policy | 长文本、标题及阅读结构 |
| 404 | 错误信息、返回入口 |

### 12.2 第二层：组件状态检测

## 13. 如何整理 ADA 无障碍问题报告？

检测出问题之后，不应该只是将 Lighthouse 或 axe 的报告截图发送给团队。

一份有价值的技术整改报告，需要让开发者能够准确复现问题、理解原因、完成修复并验证结果。

### 13.1 标准问题记录示例

<card gap={3}>
  <row align="center">
    <caption>A11Y-001</caption>
    <spacer/><badge color="danger">高优先级</badge>
  </row>
  <title size="lg">Cart Drawer 关闭后仍可通过键盘访问内部控件</title>
  <divider/>
  <caption>Affected Pages</caption>
  所有包含 Cart Drawer 的 Storefront 页面

  <caption>Component</caption>
  `cart-drawer.liquid` / `cart-drawer.js`

  <caption>Detection</caption>
  axe-core：`aria-hidden-focus`

  <caption>WCAG</caption>
  4.1.2 Name, Role, Value；另需人工评估 2.4.3 Focus Order

  <caption>Steps to reproduce</caption>
  关闭购物车抽屉，连续按 Tab，观察是否进入不可见的商品操作按钮。

  <caption>Actual result</caption>
  焦点进入已经视觉隐藏的购物车区域。

  <caption>Expected result</caption>
  关闭状态下，购物车内部控件不参与焦点导航和辅助技术访问。

  <caption>Root cause</caption>
  仅使用 transform 和 aria-hidden 隐藏抽屉，没有隔离内部交互元素。

  <caption>Recommended fix</caption>
  使用 inert 或适当的隐藏机制，并同步处理打开、关闭及焦点恢复。

  <caption>Verification</caption>
  重新运行 axe、键盘导航测试和屏幕阅读器测试。
  <divider/>
  <caption>以上为虚构的标准问题记录示例。</caption>
</card>

### 13.2 如何定义修复优先级？

团队可以使用以下内部优先级模型。

| 优先级 | 判断依据 | 示例 |
|---|---|---|
| P0 | 完全阻断关键业务 | 用户无法加购或结账 |
| P1 | 严重影响核心操作 | Cart Drawer 键盘陷阱 |
| P2 | 影响部分信息或操作 | 商品价格对比度不足 |
| P3 | 局部体验或最佳实践 | 部分不合理的标题层级 |

这是一种建议的工程管理模型，不是 WCAG 官方分级。

### 13.3 不要按问题节点数量直接分配工作

假设检测报告如下：

我不建议把无障碍检测安排在项目上线之前的最后一天。

后期再修改焦点管理、弹窗结构和异步状态，成本通常会更高。

        {#each q.o as o,j}
          <radio value={String(j)}>{o}</radio>
        {/each}
      </radio-group>
      {#if answers24[i]>=0}
        <text size="sm" color={answers24[i]===q.a?"success":"danger"}>{answers24[i]===q.a?"回答正确":"回答错误"}：{q.e}</text>
      {/if}
    </box>
    {#if i<quiz24.length-1}<divider/>{/if}
  {/each}
  <button block variant="ghost" color="secondary" onClick={()=>setAnswers24(Array(quiz24.length).fill(-1))}>重新测试</button>
</card>
