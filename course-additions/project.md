## 项目定位

这一阶段使用前面 CLI 创建或拉取的主题，完成一个可以预览、配置和验收的商品页。目标是修改一个真实 Online Store 主题并交付；从空目录实现完整可销售主题，还需要覆盖首页、列表、搜索、购物车、语言与完整布局等工作。

不要同时替换现有主题的全部商品页逻辑。先理解已有组件，再选一块明确的功能独立修改。前面的代码若标注“骨架”或“示意”，需要按本项目要求补齐，不能直接当作交付完成。

## 准备测试数据

- 一个有颜色和尺码两个 Option 的商品。
- 至少一个售罄规格，以及一个没有关联媒体的规格。
- 一张正常商品图和一种其他媒体类型。
- 一个材质 Metafield，以及一个字段为空的对照商品。
- 一个集合，商品数足以触发分页。

不需要接真实收款来验证商品选择和购物车。结账测试应使用店铺允许的测试方式。

## 先写清文件职责

| 文件或模块 | 应承担的责任 |
| --- | --- |
| 商品 JSON template | 组合页面 Sections，保存页面配置 |
| 主商品 Section | 服务端输出商品信息与配置入口 |
| 价格 / 媒体 Snippet | 复用展示逻辑 |
| 商品交互组件 | 管理选项、当前 Variant、按钮与请求状态 |
| Cart Drawer Section / 组件 | 渲染购物车内容，管理开关与焦点 |
| CSS 资源 | 控制组件布局与响应式 |

文件名取决于起始主题。不要为了与教程示例一致，强行创建第二套功能相同的 `main-product` 或购物车组件。

## 按五次可运行增量实施

### 第一次：让服务端首屏可靠

商品标题、价格、媒体、当前规格 ID 和基本表单可见。禁用 JavaScript 后，主要信息仍然存在。进入带 `?variant=` 的链接，核对首屏选择与价格是否一致。

### 第二次：让商家可以配置

选择一个说明模块，将标题和展示开关做成设置；材质来自商品 Metafield。配置数据属于 Theme，材质属于商品，分别验证。

### 第三次：完成规格选择

每次选项变化都解析当前有效 Variant，更新隐藏 ID、价格、可售状态、媒体与 URL。不存在的组合与售罄是不同状态。首次加载也必须执行一次状态同步。

不要为“避免空状态”随意选择另一个可售规格，这可能让顾客买到没有选择的商品。

### 第四次：完成购买链路

先验证普通 Product Form，再增强成 Ajax 加购。实现请求中按钮状态、错误提示、重复提交防护和成功后的购物车更新。抽屉用真实 section ID 和真实 DOM 包装结构更新。

成功响应中的 section HTML 也可能缺失或为 null，要有恢复路径，例如重新请求所需内容或导航到购物车页。不要在 UI 中虚构加购成功。

### 第五次：编辑器、移动端与发布

测试同一组件多个实例，测试编辑器重载，最后检查移动端、键盘和网络失败。运行 Theme Check 后上传未发布主题，供验收。

## 响应式与无障碍怎样验收

- 小屏上价格、规格与购买按钮不被浮层遮挡；长标题不撑破布局。
- 商品图片保留合理宽高比，切换媒体时页面不大幅跳动。
- 按钮使用真实 button，表单控件有可理解的 label。
- 抽屉打开后焦点进入抽屉，Escape 关闭，关闭后回到触发按钮。
- 错误信息可被读屏用户感知，不能只靠颜色表达售罄或失败。
- 尊重减少动画偏好；移动端不要依赖 hover 才能访问核心操作。

## 最终验收表

| 场景 | 应观察到的结果 |
| --- | --- |
| 首次访问普通商品 URL | 当前规格、隐藏 ID、价格和按钮一致 |
| 带 variant 参数访问 | 首屏与 URL 指向的规格一致 |
| 无效组合 / 售罄 | 明确区分状态，不能错误加购 |
| 快速切换与连续点击 | 请求与界面状态一致，无重复加购 |
| 加购失败 | 显示原因，可再次尝试 |
| 同规格不同 properties | Cart line 操作只影响目标行 |
| 修改购物车数量 | 金额和行内容采用服务器返回结果 |
| 前进、后退、刷新 | URL 与选择状态按既定策略恢复 |
| 编辑器重渲染 | 组件仍工作，没有重复监听 |
| 两个商品组件实例 | 互不影响 |
| 窄屏和键盘操作 | 核心购买链路可完成 |
